## 一、先分清「谁设计的」，再看「怎么进库的」

打开 Navicat 会看到 77 张表。新手第一反应是「这么多表怎么记得住」——**先别背**。先站在**学习者**的位置问三个问题：**这张表谁设计的？为什么需要它？我什么时候会真正用到它？** 按这个标准，77 张表只有 **三个来源**：

| 来源 | 表数 | 谁设计 / 谁建 | 为什么需要它（它解决什么） | 你第一次真正用到 |
|---|---|---|---|---|
| **① 框架系统表** | **26** | **RuoYi 框架原作者**设计；**你**跑 `01` 脚本导进库 | 「登录 → 认出你是谁 → 发菜单 → 记日志」。**凡是 RuoYi 后台都有这几十张，跟合同业务无关** | **M0 登录那一刻**（没 `sys_user` 谁都进不去） |
| **② 业务表** | **27** | **肇新合同系统原作者**设计；**你**跑 `03`/`04` 脚本导进库 | 合同「草拟 → 审批 → 用印 → 归档」全生命周期的数据 | **M1 开始时**（T2 第一张业务表） |
| **③ Activiti 引擎表** | **24** | **引擎启动时自己建**（一行代码不用写） | 审批流程要跑，引擎得有自己的运行时 / 历史表 | **M2 提交审批时**（M0 启动后端它就自动建好了） |

**26 + 2 + 25 + 24 = 77 张。**

> 💡 **三种来源，对你的要求完全不同——这才是你该记住的**：
> - ① **框架系统表** → 你**会用**就行（不用背，用到时回来查本文 §三）。
> - ② **业务表** → 你**要讲得出「为什么这么设计」**（答辩主要考这个，本文 §四 逐张讲）。
> - ③ **引擎表** → 你**知道它干嘛**就行（本文 §四·组⑧ 只给规律，细节归 [M2](M2-审批流与事件状态机（总览）.md)）。
>
> ⚠️ **还有第四种——「你自己设计的表」**：答案册里**根本没有** M4 的 `contract_borrow`（合同借阅），这张得你自己加。**作品集里你能说「这是我设计的表」的，就是这一类**（也是唯一一类）。

**再补一层「工程视角」**（知道即可，不影响你把业务学明白）：这 77 张不是一次建出来的，而是分**四批**、用不同方式进你库里的——

| 批次 | 表数 | 谁让它进库的 | 什么时候 | 有哪些表 |
|---|---|---|---|---|
| ① **框架底座表** | **26** | 你跑 `01-zxcm-learn-base.sql` | **M0 · T4-T5** 建库导入时 | `sys_*`（24 张）+ `gen_*`（2 张） |
| ② **非业务但必需** | **2** | 你跑 `03-missing-base-tables.sql` | **M0 之后、M1-T5 / M2 之前** | `form`（合同类型）、`act_designer`（流程设计器） |
| ③ **业务表** | **25** | 你跑 `04-biz-tables.sql` | **M1 开始前一次性建好** | `conf_*`(6) `contract_*`(11) `template_*`(7) `work_handover`(1) |
| ④ **Activiti 引擎表** | **24** | **引擎启动时自动建**（一行代码不用写） | **M0 · T7 第一次启动后端** | `ACT_*` |

> ⚠️ **别把上面两张表搞混**：「来源」表里 ② 业务表是 **27** 张，「批次」表里 ②+③ 才是 27 张——因为 `form`/`act_designer` 虽然名字不带业务前缀，**本质是业务表**（见下方「两件最容易搞混的事」）。

**⚠️ 新手最容易搞混的两件事**（照下面两句记，就不会错）：

1. **业务表不是你设计的，是原作者设计、脚本帮你导进库的。** 你要做的是**理解每张表为什么这么设计**，而不是从零写建表语句。（答案册早期确实是一张张手写 DDL，后来把 25 张一次性提取成 `04-biz-tables.sql`。见 [M1 · T2](M1-基础数据与合同CRUD（总览）.md)。）
2. **`form` 和 `act_designer` 躺在名叫「missing-base-tables」的脚本里，但它们其实是业务表。** 名字骗人——`01` 脚本的筛选条件是「只保留 `sys_` / `gen_` 开头的表」，这两张表名字对不上就被误排除了，只好单独补一个脚本。详见 §四。

**怎么验证 ④ 批是「引擎自建」而不是脚本建的**（一句话自查）：

```sql
SELECT TABLE_NAME, CREATE_TIME FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'zxcm' AND TABLE_NAME LIKE 'ACT%' ORDER BY CREATE_TIME LIMIT 1;
```

实测 `ACT_GE_PROPERTY` 的建表时间比 `sys_menu` 晚 **36 秒**——那 36 秒就是 Spring 启动、Activiti 初始化引擎的时间。所以 ④ 批不是脚本建的，是**应用启动的副作用**。

**怎么自查表建全了没有**：

```sql
SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA='zxcm';
```

M0 跑完 `01` + 启动后端后应是 **50** 张（26 系统表 + 24 引擎表）；再跑完 `03` / `04` 后应是 **77** 张。

**三种来源分别在哪一节详解**：

| 来源 | 表数 | 详解位置 |
|---|---|---|
| ① 框架系统表 | 26 | **§三**（底座主体，逐张讲） |
| ② 业务表（含 `form` / `act_designer`） | 27 | **§四 · 组①~组⑦**（逐张讲） |
| ③ Activiti 引擎表 | 24 | **§四 · 组⑧**（只给分组规律，细节归 [M2](M2-审批流与事件状态机（总览）.md)） |

## 二、关系总图

先看**权限链**（这是整个底座的主干，答辩必问）：

```
   sys_user ──sys_user_role───► sys_role ──sys_role_menu───► sys_menu
      │                            │
      │                            └──sys_role_dept──────► sys_dept     ← 框架数据权限(自定)
      │
      ├──sys_user_dept──────────► sys_dept                            ← 业务数据权限(本部门/本部门及以下)
      ├──sys_user_post──────────► sys_position                        ← 岗位（本学习版空表）
      └──sys_user_manage ─(自关联)─► sys_user                          ← 谁管谁（一对一交接）
```

再看**组织和租户**：

```
   sys_dept (PARENT_ID 自关联，ANCESTORS 存祖级链 "0,100")
      └── sys_user.DEPT_ID 指向「默认部门」，多部门走 sys_user_dept

   sys_tenant (一个租户)
      ├── sys_tenant_module ──► sys_business_module      ← 租户能买哪些模块
      └── sys_business_module_menu ──► sys_menu          ← 模块包含哪些菜单
```

**一句话记忆**：`sys_user` 是中心，向左连「组织」（dept / position / user_manage），向右连「权限」（role → menu）。字典、参数、日志、存储这四组是**挂在主干旁边的工具表**，不属于权限链。

### 业务表关系总图（合同那条线）

底座表管「谁能用系统」，业务表管「合同怎么流转」。合同这股数据的中心是 `contract_draft`：

```
   conf_signing_subject(签约主体)      conf_contract_counterpart(合作方/相对方)
              ▲  SUBJECTS(JSON)                     ▲  PARTNERS(JSON)
              └──────────────┬───────────────────────┘
                             │
                    ┌────────┴─────────┐
                    │  contract_draft  │  ← 合同本体（系统的心脏，85 列宽表）
                    └──┬────┬────┬─────┘
                       │    │    └──────── contract_point_log（事件流水：到底发生了什么，只增不改）
                       │    └───────────── contract_draft_files（合同文件，带版本 V1.0/V1.1）
                       └────────────────── contract_draft_partnerids（相对方关联表）
                                                │ 审批走完 → 抄一份快照
                                                ▼
                       contract_his / contract_his_files（合同历史快照，只读不写）

  合同类型 form ──INSTANCE_DEF_KEY──► act_designer（业务侧流程定义）
                                            │  EN_CODE = 引擎侧 ACT_RE_PROCDEF.KEY_
                                            ▼
                              contract_audit_form（审批单）── contract_remarks（审签意见）

  模板线：template_contract（壳）──template_link_relation──► template_clause / template_element
  用印线：contract_seal ──► contract_seal_notes（用印流水，法律凭证，只增不改）
  文件线：conf_file ← 统一文件表，靠 MODULE 列区分来源（M1 合同附件 / M3 模板文件 / M4 双章合同都存它）
```

**一句话记忆**：**签约主体 + 合作方 → 合同本体 `contract_draft` → 审批（`form`→`act_designer`→`contract_audit_form`）→ 快照（`contract_his`）→ 用印（`contract_seal*`）**。模板线、文件线是围绕它转的配套设施。

## 三、底座表逐张详解（26 张 · 框架系统表）

**这 26 张是 RuoYi 框架自带的系统表，不是你为合同系统设计的。** 它们跟业务无关——用户、角色、菜单、部门、字典、日志，任何 RuoYi 后台都有。**你的角色是「会用」**：知道哪张表干嘛、用到了回来查字段就行。

字段表格只列**承载语义的列**。每张表都有 `CREATE_BY / CREATE_TIME / UPDATE_BY / UPDATE_TIME` 这套审计四件套（有的还有 `DEL_FLAG`、`TENANT_ID`），下文不再逐个重复。

> 📖 **本节讲的是 ① 框架系统表（26 张）**。② 业务表（27 张）在 **§四**。

### 组 ① 权限与组织（11 张）——底座的主干

#### 1. `sys_user` 用户信息表（行 3072）

| 字段 | 类型 | 说明 |
|---|---|---|
| `USER_ID` | decimal(20,0) PK | 主键。**注意是 decimal 不是 bigint**，全项目 ID 都这样 |
| `TENANT_ID` | varchar(64) | 租户标识，本项目只有 `00000000` |
| `TENANT_ADMIN` / `SYSTEM_ADMIN` | char(1) | 租户管理员 / 系统管理员开关。`zxcmAdmin` 的 SYSTEM_ADMIN=1 |
| `DEPT_ID` | decimal(20,0) | **默认部门**。注意仅仅是「默认」，一人多部门靠 `sys_user_dept` |
| `USER_NAME` | varchar(30) | 登录账号 |
| `PASSWORD` | varchar(100) | BCrypt 哈希，不是明文 |
| `SECRET_LEVEL` | char(1) | **密级**：1绝密 2机密 3秘密 4一般（默认4）。业务表要继承这个做密级过滤 |
| `CONFIG` | text | 用户自定义配置（前端主题、每页条数等），前端 `localStorage` 的落库版 |
| `JOB_NO` | varchar(30) | 工号 |
| `PASSWORD_CHANGE` / `RESET_PASSWORD_TIME` | char(1) / datetime | 强制改密标记 + 上次重置时间 |

**谁在读写**：`SysUserMapper`（+`SysUserMapper.xml`）、`SysUserServiceImpl`、`SysUserController`（`/system/user`）、`SysProfileController`（`/system/user/profile` 个人中心）。
**什么时候用到**：登录、用户管理页、所有 `create_by` 记录的展示、@提及选人。
**删了会怎样**：整个系统登不上去——`UserDetailsServiceImpl` 第一句就是查它。

**⭐ 顺带记住一个活例子**：`SysUserMapper.selectPageUserListWithP()`（第 48 行）上挂了
```java
@DataPermission(value = {@DataColumn(key = "userId", value = "u.user_id")},
                 resource = DataPermissionResource.workPermission)
```
这是**在裁剪后的学习版里，唯一一处业务数据权限还在跑的地方**（工作交接选人的那个用户列表）。看懂这一行就看懂了 `ContractPermission` 那套机制怎么接进去的——详见 §5.1。

#### 2. `sys_dept` 部门表（行 1653）

| 字段 | 说明 |
|---|---|
| `DEPT_ID` | PK |
| `PARENT_ID` | 父部门 ID，树的边 |
| `ANCESTORS` | **祖级列表**，如 `0,100`。空间换时间的经典做法：查「某部门及以下」不用递归，`find_in_set(100, ancestors)` 一把梭 |
| `DEPT_NAME` / `DEPT_CODE` / `DEPT_TYPE` | 名称 / 编码 / 类型（`company`、`dept`…字典 `dept_type`） |
| `LEADER` / `ASSISTANT` | **负责人 / 助理的用户 ID**（不是名字！）。业务数据权限的 `MYDEPT` 系列靠它 |
| `LEADER_NAME` / `ASSISTANT_NAME` | 上面两个字段的冗余中文名，避免每次 join `sys_user` |
| `STATUS` / `DEL_FLAG` | 停用 / 逻辑删除 |

**实测数据只有 2 行**：`100 总公司(ancestors='0')` 和 `2075148338088488961 测试部门(ancestors='0,100')`。
**谁在读写**：`SysDeptMapper`(+xml)、`SysDeptServiceImpl`、`SysDeptController`（`/system/dept`）。另外 `SysDeptServiceImpl.getMyDept()`（453 行）被数据权限引擎调用。
**什么时候用到**：部门树、数据权限、台账按部门汇总。
**⭐ 容易踩**：`LEADER` 存的是用户 ID 字符串，不是用户名。写 SQL 时 `LEADER = user.getUserId()` 而不是 `= 'zxcmAdmin'`。

#### 3. `sys_role` 角色信息表（行 2502）

**这是全项目字段最值钱的一张表**，答辩时能讲 10 分钟。

| 字段组 | 字段 | 说明 |
|---|---|---|
| 基本 | `ROLE_ID` / `ROLE_NAME` / `ROLE_KEY` / `ROLE_SORT` | 权限字符串如 `admin`、`common` |
| **框架数据范围** | `DATA_SCOPE` char(1) | 1全部 2自定 3本部门 4本部门及以下 5仅本人 |
| **业务数据范围 ×10** | `DRAFT_PERMISSION`(草拟)、`CONTRACT_PERMISSION`(合同)、`DASHBOARD_PERMISSION`(仪表盘)、`COLLAB_PERMISSION`(协同)、`LEDGER_PERMISSION`(台账)、`STAMP_PERMISSION`(用印)、`PLAN_PERMISSION`(计划)、`COMPARE_PERMISSION`(比对)、`PARTNER_PERMISSION`(相对方)、`WORK_PERMISSION`(工作交接) | **每列一个 char(1)**，默认 `'5'`，取值走 `ContractPermission` 枚举（7 档） |
| 前端树行为 | `MENU_CHECK_STRICTLY` / `DEPT_CHECK_STRICTLY` | 「父子联动」开关 |
| 其他 | `STATUS` / `DEL_FLAG` / `TENANT_ID` | |

**实测 11 行**角色。**谁在读写**：`SysRoleMapper`(+xml)、`SysRoleServiceImpl`、`SysRoleController`（`/system/role`）、`SysTenantServiceImpl`（348 行新建租户时复制角色）。
**什么时候用到**：角色管理页、`/getRouters` 拿菜单、每一次带 `@DataPermission` 的查询。

**⭐ 面试金句**：一个 `DATA_SCOPE` 管不到业务，所以他们**横向加了 10 列**，让「审批完成的合同」和「草拟中的合同」可以给不同范围——比如专员能看自己的草稿，但只能看本部门已审批的合同。这是从 RuoYi 原生扩展出来的设计。

#### 4. `sys_menu` 菜单权限表（行 2131）

| 字段 | 说明 |
|---|---|
| `MENU_ID` / `MENU_NAME` / `PARENT_ID` / `ORDER_NUM` | 树的四件套 |
| `PATH` / `COMPONENT` / `QUERY_PARAM` | **前端路由三要素**：路由地址、组件路径、路由参数。`/getRouters` 把它们原样吐给前端 |
| `MENU_TYPE` char(1) | **M目录 / C菜单 / F按钮**。F 类型的只有 `PERMS` 没有 `PATH`，是权限点不是页面 |
| `PERMS` | 权限标识，如 `system:user:add`。前端 `v-hasPermi` 指令、后端 `@SaCheckPermission` 都读它 |
| `IS_FRAME` / `IS_CACHE` / `VISIBLE` / `STATUS` | 外链 / keep-alive / 显示隐藏 / 停用 |
| `ICON` | 图标名（Element UI 的 icon class） |
| `TENANT_FLAG` varchar(64) | **本项目的扩展**：`0`租户菜单 `1`管理菜单 `2`租户+管理。超管租户和普通租户看到的菜单不一样，靠它分流 |
| `COMPONENT` 特殊值 | `Layout`=主框架、`ParentView`=只做嵌套的壳、`InnerLink`=内嵌外链 |

**实测 75 行**（改造后剩 2 个顶级目录，见 M0 计划 Task 5）。
**谁在读写**：`SysMenuMapper`(+xml)、`SysMenuServiceImpl`、`SysMenuController`（`/system/menu`）、`SysIndexController.getRouters()`（你实测过的那条链）。
**什么时候用到**：登录后渲染侧边栏、按钮级权限、`sys_role_menu` 的勾选来源。
**⚠️ 陷阱**：`COMPONENT` 是字符串路径，拼错了前端不报错、只是**白屏或者 404**——前端调试最难查的一类问题。

#### 5. `sys_position` 岗位信息表（行 2475）

| 字段 | 说明 |
|---|---|
| `ID` | PK |
| `full_name` / `en_code` / `type` | 岗位名称 / 编号 / 类型 |
| `property_json` | 扩展属性 JSON |
| `organize_id` / `flow_code` | 机构主键 / 流程编号 |

#### 17. `sys_err_log` 错误日志（行 2040）

| 字段 | 说明 |
|---|---|
| `ID` | PK，**类型是 `decimal(65,30)`**——非常规，能存 65 位数字 |
| `CLASS_NAME` / `METHOD_NAME` | 出错位置 |
| `EXCEPTION_NAME` | 异常类型，如 `java.lang.NullPointerException` |
| `ERR_MSG` | 错误信息 |
| `STACK_TRACE` | 完整堆栈（longtext） |

**谁在写**：**logback Appender**，不是 AOP、不是手写业务代码。实现在
`ruoyi-base/ruoyi-system/.../appender/DbErrorLogAppender.java`：
```java
@Component
public class DbErrorLogAppender extends UnsynchronizedAppenderBase<ILoggingEvent> {
    @PostConstruct
    public void init() {
        ThresholdFilter filter = new ThresholdFilter();
        filter.setLevel("ERROR");           // 只接 ERROR 级别
        ...
        context.getLogger("ROOT").addAppender(DbErrorLogAppender.this);  // 挂到 ROOT
    }
}
```
**⚠️ 关键：它在任何 `logback*.xml` 里都搜不到！** 因为它是 `@Component` + `@PostConstruct` **用代码把自己挂到 ROOT logger 上**的。你要是去 `logback.xml` 里找它，会白找半天——我第一次就搜空了。
**过滤规则**：`if (className.equals("com.xxl.job.core.util.XxlJobRemotingUtil")) return;`——XXL-JOB 连不上调度中心时不写库，否则会刷爆。（本项目 `xxl.job.enabled: false`，暂时无关。）
**实测 38 行**。**⚠️ 没有管理页面**：全项目 **没有 `SysErrLogController`**。有 `SysErrLogMapper` + `SysErrLogServiceImpl`（甚至还有 `cleanExpiredLog()` 清理方法），但**没有 Controller**，所以后台菜单里找不到它——只能直接查库。
**⭐ 面试答法**：「错误日志我用的不是 AOP，是自定义 logback Appender，挂 ROOT logger + ERROR 阈值过滤。好处是**代码里任何一个 `log.error()` 都会自动落库**，不需要开发者在 Controller 上手动加注解。」

### 组 ⑧ Activiti 引擎表（24 张）—— 只给规律，细节归 M2

## 五、三个「一表三用」的深坑（面试核心区）

### 5.1 数据权限有**三套引擎**，不是一套

同样叫「看不到别人的数据」，本项目有**三个完全独立的机制**。答辩时能把这套讲清楚，比背十个 CRUD 有说服力。

#### 机制一：框架数据范围 —— 引擎 `sys_role.DATA_SCOPE`（5 档）

枚举：`ruoyi-common/.../enums/DataScopeType.java`

```java
ALL            ("1", "", "")
CUSTOM         ("2", " #{#deptName} IN ( #{@sdss.getRoleCustom( #user.roleId )} ) ", "")
DEPT           ("3", " #{#deptName} = #{#user.deptId} ", "")
DEPT_AND_CHILD ("4", " #{#deptName} IN ( #{@sdss.getDeptAndChild( #user.deptId )} )", "")
SELF           ("5", " #{#userName} = #{#user.userId} ", " 1 = 0 ")
```

- **靠谁**：`sys_role_dept`（只有 CUSTOM 用）；`sys_dept.ANCESTORS`（DEPT_AND_CHILD 用 `find_in_set`）
- **`@sdss` 是什么**：SpEL 里的 bean 引用，指向 `SysDataScopeServiceImpl`（`@Service("sdss")`）
- **谁来解析**：`ruoyi-framework/.../handler/PlusDataPermissionHandler.java`
- **怎么触发**：Mapper 方法上写 `@DataPermission({@DataColumn(key = "deptName", value = "d.dept_id"), ...})`

#### 机制二：业务数据范围 —— 引擎 `sys_role.*_PERMISSION`（10 列 × 7 档）

枚举：`ruoyi-common/.../enums/permissionType/ContractPermission.java`

```java
ALL            ("1", "", "")
CUSTOM         ("2", " 1=0 ", "")
DEPT           ("3", " #{#userId} IN #{@sdss.getDeptUser( #user )} ", "")
DEPT_AND_CHILD ("4", " #{#userId} IN ( #{@sdss.getDeptAndChildUser( #user )} )", "")
SELF           ("5", " #{#userId} = #{#user.userId} ", " 1 = 0 ")
MYDEPT         ("6", " #{#userId} IN ( #{@sdss.getMyDeptUser( #user )} )", " 1 = 0 ")
MYDEPT_AND_CHILD("7"," #{#userId} IN ( #{@sdss.getMyDeptAndChildUser( #user )} )", " 1 = 0 ")
```

- **靠谁**：`sys_user_dept`（一人多部门）；`sys_dept.LEADER` / `ASSISTANT`（「我负责的部门」）
- **和机制一的关键差别**：机制一按 **`dept_id`** 过滤（数据属于哪个部门），机制二按 **`user_id`** 过滤（数据属于谁）。因为合同是「人」的资产，不是「部门」的资产。
- **多出的 6、7 档「我负责的部门」**：靠 `SysDeptServiceImpl.getMyDept()`，SQL 就是
  ```java
  wrapper.eq(SysDept::getLeader, user.getUserId()).or().eq(SysDept::getAssistant, user.getUserId());
  ```
  「我是这个部门负责人 → 这个部门的合同我能看」。这是纯业务扩展，框架里没有。
- **怎么触发**：`@DataPermission(value={@DataColumn(key="userId", value="u.user_id")}, resource = DataPermissionResource.xxxPermission)`
  `resource` 是哪个枚举值，就去读 `sys_role` 的哪一列——**反射取值**：
  ```java
  String resourceP = (String) ReflectUtil.getFieldValue(role, dataPermission.resource().getIndex());
  ```
  所以 `DataPermissionResource` 枚举的 `index` **必须和 `sys_role` 的字段名一一对应**，改列名会静默失效。

  > 💡 **一句话说人话**：「反射取值」就是**按名字去对象里翻字段**——枚举的 `index` 写着 `partnerPermission`，Java 就拿这个字符串去 `RoleDTO` 上找一个同名的字段读出来。名字打错一个字母**不会报错**，但读回来是 `null`，权限就静默变成「看全部」（D3 §8.3 那个安全点）。
- **学习版里的活例子**：`SysUserMapper.selectPageUserListWithP()`（`resource = workPermission`）

#### 机制三：`sys_user_manage` —— 按人交接

不属于上面任何一套，是**独立的表 + 独立的查询**。`manager_user` 管 `managed_users`。实测 0 行，但表在、Controller 在。

#### 📌 三套机制对照表（背下来）

| | 机制一 框架 | 机制二 业务 | 机制三 交接 |
|---|---|---|---|
| 存在哪个字段 | `sys_role.DATA_SCOPE` | `sys_role` 的 10 个 `*_PERMISSION` | `sys_user_manage` 表 |
| 档数 | 5 | 7 | 无档，纯名单 |
| 过滤列 | `dept_id` | `user_id` | 用户 ID 名单 |
| 依赖表 | `sys_role_dept`、`sys_dept.ANCESTORS` | `sys_user_dept`、`sys_dept.LEADER/ASSISTANT` | `sys_user_manage` |
| 枚举 | `DataScopeType` | `ContractPermission` | 无 |
| 触发注解 | `@DataPermission(resource=base)` | `@DataPermission(resource=xxxPermission)` | 手写 |

**⭐ 为什么要有机制二而不是复用机制一**：因为一个角色对不同业务对象要不同范围。法务专员：**草拟中的合同**只能看自己的（SELF），但**审批完成的合同**整个部门都能看（DEPT）。一个 `DATA_SCOPE` 列表达不了两个维度，所以他们横向加到 10 列。**这是本项目在 RuoYi 上最有价值的架构扩展，面试一定要讲。**

### 5.2 三张日志表 = 三种写入机制

| 表 | 写入方式 | 实现位置 | 触发条件 |
|---|---|---|---|
| `sys_oper_log` | **注解式 AOP** | `LogAspect` 切 `@Log` | Controller 上写了 `@Log` |
| `sys_logininfor` | **业务代码手写** | `SysLoginService` / `SysRegisterService` 调 `recordLogininfor()` | 登录/登出/注册 |
| `sys_err_log` | **logback Appender** | `DbErrorLogAppender` 挂 ROOT logger | 任何 `log.error()` |

**三者都带 `@Async` 或异步**（`recordOper`、`recordLogininfor` 都有 `@Async`；Appender 本身在日志线程上），**不阻塞主请求**。

**面试问法**：「为什么登录日志不用 AOP？」
**答**：「因为登录接口执行时**还没有登录用户**，AOP 拿不到 `oper_name`；而且登录失败要分 IP 限次，得精确记录每种失败原因（验证码过期 / 密码错误 / 超过重试次数），这些语义 AOP 的通用模型表达不了，所以用手工埋点。」

**面试问法**：「为什么要有两张错误表（`sys_oper_log.ERROR_MSG` 和 `sys_err_log`）？」
**答**：「不是一回事。`sys_oper_log` 记的是**业务请求失败**（一个接口抛异常了），有用户名、URL、请求参数，是**审计视角**；`sys_err_log` 记的是**任何 `log.error()`**，包括定时任务、异步线程里的异常，没有 HTTP 上下文，是**排障视角**。前者给管理员看『谁干了什么失败了』，后者给开发看『哪儿崩了』。」

### 5.3 逻辑删除 `DEL_FLAG` ≠ 枚举

**⚠️ 这个坑我在读表时踩到了**：`DEL_FLAG` 的注释写的是「**0 未删除 2 已删除**」。

- **不是 `0/1`**，是 `0/2`！
- 原因是 `1` 被别的状态占了。`sys_menu` 里 `VISIBLE` 是「0显示 1隐藏」，`STATUS` 是「0正常 1停用」，`IS_FRAME` 是「0是外链 1否」……**这个项目的所有 `char(1)` 状态位编码完全不统一**。

**答辩风险**：写 SQL 时想当然写 `WHERE DEL_FLAG = 1` 会**查出全部数据**。另外 MyBatis-Plus 的逻辑删除是全局配置的（`@TableLogic`），手写 XML 时**不会自动加这个条件**——`SysPostMapper.xml` 那种手写 SQL 里如果漏了 `DEL_FLAG`，就会查出已删除数据。

**建议**：统一用 Java 实体走 MyBatis-Plus（自动带逻辑删除），少手写 SQL；非要手写，先确认那三五个 `char(1)` 状态位的编码。

> 💡 **一句话说人话**：这个项目的 `char(1)` 状态位**各表各写各的**（同是「0/1」，有的 1 表示「是」、有的 1 表示「停用」）。写 SQL 前**先 `SHOW CREATE TABLE 表名` 看列注释**，别凭直觉写 `WHERE DEL_FLAG = 1`——那会查出**全部**数据（含已删除的）。

## 六、面试问法与参考答法

**Q1：为什么主键用 `decimal(20,0)` 而不是 `bigint` 或者自增？**
A：用的是**雪花算法**生成的分布式 ID，19 位数字，所以 `decimal(20,0)` 兜得住。好处是分库分表时不用改、ID 不泄露业务量；代价是**占空间比 bigint 大、索引效率略低**。另外注意：Java 侧接收 19 位 long 到前端**必须序列化成字符串**，否则 JS 的 Number 精度只有 53 位会丢精度——所以你会看到 `@JsonSerialize(using = ToStringSerializer.class)`。

**Q2：部门树的「查某部门及以下」怎么实现的？**
A：`sys_dept.ANCESTORS` 存祖级链（根是 `0`，子部门是 `0,100`）。查「100 及以下」直接 `find_in_set(100, ancestors)`，一次查询搞定，不需要递归。**代价是移动部门时要批量重写子树的 `ANCESTORS`**——这是空间换时间。

**Q3：用户和部门是一对多还是多对多？**
A：**两套并存**。`sys_user.DEPT_ID` 是**默认部门**（一对多，一个部门多个用户），`sys_user_dept` 是**兼职部门**（多对多，一人多部门）。业务数据权限按后者算。加 `sys_user_dept` 是因为合同管理里法务专员常兼管多个部门，单 `DEPT_ID` 表达不了。

**Q4：一个角色对「草稿」和「已审批合同」能设不同可见范围吗？**
A：能。这是本项目在 RuoYi 原生 `DATA_SCOPE` 之上**横向扩展了 10 列**（`DRAFT_PERMISSION` 到 `WORK_PERMISSION`），每列独立走 `ContractPermission` 枚举的 7 档。触发方式是 `@DataPermission(resource = DataPermissionResource.xxxPermission)`，Handler 用**反射**按枚举 `index` 去读 `sys_role` 对应列。

**Q5：菜单权限和数据权限有什么区别？**
A：**菜单权限管「能不能进这个页面/能不能点这个按钮」**，靠 `sys_role_menu` → `sys_menu.PERMS` → 前端 `v-hasPermi` + 后端 `@SaCheckPermission`；**数据权限管「进去以后能看到哪些行」**，靠 `sys_role.*_PERMISSION` → `@DataPermission` → 往 SQL 里拼 `WHERE`。前者是粗粒度、静态的；后者是细粒度、动态的。

**Q6：`/getRouters` 为什么返回菜单树，不返回菜单列表？**
A：前端要直接塞给 vue-router，`children` 嵌套结构省得前端再组树；更重要的是**`COMPONENT` 字段是后端配的组件路径**，前端 `import(@/views/${component})` 动态加载，所以加菜单**不用改前端代码**。这是「权限驱动路由」的核心。

**Q7：操作日志怎么保证不影响接口性能？**
A：AOP 里最后一句 `recordOper()` 上加了 `@Async`，丢到线程池落库，主请求不等待。**代价是可能丢日志**（线程池满了 / 应用被 kill），所以真正的审计场景要同步写。

**Q8：字典改了为什么不生效？**
A：字典走 Redis 缓存。`SysDictDataServiceImpl` 增删改时会清 `CacheConstants.SYS_DICT_KEY`。**直接改库不会清缓存**，必须走后台接口改，或者手工删 key。

**Q9：`sys_config` 和 `sys_dict_data` 都存配置，区别是什么？**
A：**`sys_dict_data` 是「枚举值的候选集」**（下拉框里有哪些选项，多行、有序、带 label/value）；**`sys_config` 是「系统的单个开关或参数」**（一个 key 一个值，值可以是 JSON）。选人用字典，选行为用参数。

**Q10：这套系统是多租户吗？**
A：**是 SaaS 架构但当前跑单租户**。所有表都有 `TENANT_ID`，有 `sys_tenant` / `sys_tenant_module` / `sys_business_module_menu` 一整套「租户 → 模块 → 菜单」授权链，MyBatis-Plus 也有租户插件拦截。但底座数据只有 `00000000` 一个租户，所以实际是单租户运行。**答题技巧**：主动说「架构预留了多租户，当前部署是单租户」，比含糊说「有多租户」稳。

## 九、🎤 一分钟讲法（对着面试官讲）

被问「你这套系统的权限底座是怎么设计的」，照下面这段讲，**一分钟内讲完**：

> 「整套权限的底座就一条链：**用户 `sys_user` → 角色 `sys_role` → 菜单 `sys_menu`**，中间靠 `sys_user_role`、`sys_role_menu` 两张多对多关联表接起来。`sys_menu` 是**一张表三用**——`MENU_TYPE` 区分目录 M / 菜单 C / 按钮 F，权限码就存在它的 `PERMS` 列里，这是**功能权限**。
>
> 数据权限我们做了**三套引擎**：第一套是 RuoYi 原生的 `sys_role.DATA_SCOPE`（5 档，按数据属于**哪个部门**过滤）；第二套是我们在它旁边**横向加了 10 列 `*_PERMISSION`**（7 档，按数据属于**哪个人**过滤）——因为合同是「人」的资产不是「部门」的资产，而且同一个角色对「草稿中的合同」和「已审批的合同」要能配不同范围；第三套是 `sys_user_manage` 表，按人做休假交接。
>
> 三套用的是同一个机制：Mapper 方法上标 `@DataPermission`，MyBatis-Plus 拦截器往 SQL 的 `WHERE` 里拼条件——**同一个接口、同一份代码，不同的人看到不同的行**。」

如果面试官只给你 30 秒，就讲这一句：

> 💡 **一句话说人话**：**`sys_user` 是中心，向左连组织、向右连权限；功能权限管「能不能进这个页面」，数据权限管「进去以后能看哪些行」，我们的数据权限有三套引擎。**

**⚠️ 讲这段时最容易踩的两个坑**：

1. **别说「权限码在角色表上」**。权限码在 `sys_menu.PERMS`；角色表上放的是**数据范围**（`DATA_SCOPE` 和那 10 个 `*_PERMISSION`）。这两样经常被混着说，面试官一听就知道你没分清。
2. **别顺嘴提「文件走 OSS」**。`sys_oss` / `sys_oss_config` 两张表在本项目是**空壳、零 Java 代码**，文件走的是 `ruoyi.profile` 本地磁盘（见 §三·组④）。主动说「遗留未启用」比被问住强。

> ⭐ **进阶版收尾**（面试官明显懂行时再讲）：
> 「这套设计里我觉得最值得讲的是**第二套引擎**。原生 RuoYi 一个 `DATA_SCOPE` 管所有业务，但我们发现**一个角色对不同业务对象要不同的可见范围**——法务专员草拟中的合同只能看自己的，但审批完成的合同整个部门都能看。一个 `DATA_SCOPE` 列表达不了两个维度，所以我们横向扩展成 10 列，每列独立走 `ContractPermission` 枚举的 7 档，用 `@DataPermission(resource = xxxPermission)` 指定读哪一列。**这是本项目在 RuoYi 上最有价值的一处扩展。**」
