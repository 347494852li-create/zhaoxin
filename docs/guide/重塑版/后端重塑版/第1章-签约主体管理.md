# 第 1 章 · 签约主体管理

> 这是「合同生命周期」的第一站，也是**全书最简单、但最完整**的一个功能。它没有任何复杂业务，正好用来把第 0 章认识的所有东西（分层、`R`、`BaseEntity`、五件套、三件套）**完整敲一遍**。
>
> **本章第一次讲透**：① Sa-Token 鉴权到底怎么工作；② 逻辑删除、雪花 ID 在代码里长什么样；③ 一个「标准 CRUD 功能」的完整写法，后面每一章都是它的变体。
>
> **本章你会碰到的表**：`conf_signing_subject`（唯一一张业务主表）+ 几张框架表（`sys_menu` / `sys_role_menu` / `sys_dict_data` / `sys_oper_log`）。

> **零基础先补概念（不懂这四个词，后面的代码会像天书）**
>
> - **Controller / Service / Mapper 分层**：Controller 负责接请求和返回结果；Service 写业务规则（例如「名称不能重复」）；Mapper 只执行数据库操作。看 `zxcm-contract/src/main/java/com/ruoyi/conf/controller/TSigningSubjectController.java:86-88`，Controller 里只有一行「转给 Service」，没有任何 SQL。
> - **Entity / BO / VO**：Entity 对应数据库表（`zxcm-contract/src/main/java/com/ruoyi/conf/domain/TSigningSubject.java:37`）；BO 接前端参数（`zxcm-contract/src/main/java/com/ruoyi/conf/domain/bo/TSigningSubjectBo.java:40`）；VO 返回给前端（`zxcm-contract/src/main/java/com/ruoyi/conf/domain/vo/TSigningSubjectVo.java:37`）。一句话：**入库看 Entity，收参看 BO，出参看 VO**。
> - **Wrapper（条件构造器）**：MyBatis-Plus 的「查询积木」。`eq` 是等于、`like` 是模糊匹配、`orderByDesc` 是倒序，拼完交给 Mapper 执行。本章的 `buildQueryWrapper`（`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:112-126`）就是标准例子。
> - **分组校验（JSR-303 groups）**：同一个 BO 上写一套校验注解，但用 `groups` 区分「新增时查哪几条、修改时查哪几条」。例如 `id` 只在修改时必填（`TSigningSubjectBo.java:46`），新增当然没有 id。

## 一、这部分是做什么的？

### 1.1 业务含义

**「签约主体」= 我方公司自己**。签一份合同，必然有两方：我方和对方。签约主体就是「我方」这个身份——比如「山西肇新科技有限公司」。

为什么要单独管理它？因为：
- 一家集团可能有好几个法人主体，签合同时要选「用哪个主体签」；
- 主体的**统一社会信用代码、法人、银行账号、联系人**这些信息，合同上要反复用到；
- 主体的**可用状态**要能开关（某主体停止使用了就不该再出现在选项里）。

所以这一章是「**基础数据维护**」——把将来要反复引用的主数据先录进去、能增删改查。

### 1.2 页面长什么样（前端）

页面在 `zxcm-ui/src/views/conf/signingSubject/index.vue`，功能就是标准后台的「**列表 + 搜索 + 新增/修改弹窗 + 删除**」：

- 顶部搜索区：按「主体编号 / 主体名称 / 企业经营状态」查找（`index.vue:13-92`）
- 中间表格：显示编号、名称、统一社会信用代码、经营状态、可用状态、创建时间（`index.vue:123-201`）
- 「新增 / 导入」按钮（`index.vue:96-115`）
- 每行的「修改 / 删除」按钮（`index.vue:184-199`）
- 「可用状态」是个开关，一拨就调接口改状态（`index.vue:169-175`）
- 新增/修改用同一个弹窗（`index.vue:213-590`），里面还嵌套了「财信息（银行）」和「联系人」两个可以动态增删的卡片列表

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么「新增」和「修改」用同一个弹窗、同一套代码？

看前端 `index.vue:793-833`：点「确定」时，代码只判断**有没有 `id`**——有 `id` 走 `updateSigningSubject`，没有走 `addSigningSubject`。

后端也一样：新增走 `POST`、修改走 `PUT`（`TSigningSubjectController.java:147` 和 `:159`），但两者**共用同一个 BO**，只是校验分组不同（新增用 `AddGroup`、修改用 `EditGroup`，见 `:148` 和 `:160`）。

**为什么这么设计？** 因为「新增」和「修改」的**表单字段、弹窗布局、校验规则 99% 一样**，差别只有一个「id 有没有值」和「个别字段必填与否」。抽成一套，代码量减半、维护点减半。**这是企业开发里的通用套路**，你后面每个功能都会看到它。

### 2.2 最关键的设计取舍：为什么「银行信息」「联系人」不用子表，而是塞进一个 JSON 字符串？

这是本章最值得讲的设计点。看 Entity `TSigningSubject.java:120-129`：

```java
/** 银行账号 数组[]，包含所属银行、开户行、账号 [...] */
private String bankJson;

/** 联系人信息 数组[] 包括姓名、称呼、部门、岗位、联系方式、邮箱 [...] */
private String contacts;
```

一个主体可以有**多个**银行账号、**多个**联系人。教科书做法是建两张子表 `conf_signing_subject_bank`、`conf_signing_subject_contact`（一对多）。但本项目选择**把它们序列化成 JSON 字符串，存在主表的一个 varchar 字段里**。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 建子表（一对多） | 规范、能按字段查询、能做外键 | 要多两张表、两个 Entity、两个 Mapper；查询列表要 join 或二次查询；前端提交要处理「删哪些增哪些」 |
| **JSON 字符串（选用）** | **一张表搞定**，前端提交一个数组、后端存一个字符串 | 没法用 SQL 按「银行账号」检索；数据没有强 schema 约束 |
| 独立文档数据库（MongoDB） | 天然适合这种结构 | 引入新中间件，本项目全部表都在 MySQL（初始化脚本共 91 个 `CREATE TABLE`），不值当 |

**架构师的判断依据**：银行信息、联系人**永远只跟着主体一起被读、一起被改，从不单独查询**。既然「没有独立查询需求」，就没必要为它建独立表——**建表的成本（多两张表 + 相关 CRUD）大于收益**。

前端的处理也印证了这一点（`index.vue:801-802`）：提交前把数组 `JSON.stringify` 成字符串；回显时（`index.vue:775-785`）再 `JSON.parse` 回来。

> **面试怎么答**：这个设计体现的是「**按查询需求决定建模方式**」。如果面试官追问「那这样怎么搜联系人？」——你就答：「业务上不需要按联系人检索，如果将来需要，再迁移成子表即可；这是有意识的取舍，不是偷懒。」

### 2.3 为什么 `searchSubject` 这个接口要写一堆「最少 4 个字、结果不能超过 1 条」的诡异逻辑？

看 `TSigningSubjectController.java:94-116`。这个检索接口是**半公开的**（合同起草时，外部用户要能查到主体）。如果谁都能拿它**批量拉走全部主体信息**（公司名、信用代码、法人），那是**数据泄露**。

所以它做了**权限分级**：

1. 如果当前用户有 `contract:subjectAll:search` 权限 → 正常返回（`:100`）
2. 没有该权限 → 强制三个限制（`:103-114`）：
   - 搜索词**至少 4 个字**（防止用单字「公」把一堆公司刷出来）
   - 结果**超过 1 条就报错**（逼你输入完整公司名，一次只能确认「这一家是不是你要的」）
   - **0 条也报错**（避免探测）

**这是「接口级的越权防护」**——不是简单地「有权限/没权限」，而是**对没权限的人降低数据暴露面**。这个思路在企业里叫「**最小必要信息**」。面试官如果问「你们怎么防止接口被刷数据」，这个例子非常硬。

### 2.4 为什么删除要做成「逻辑删除」+「发事件通知下游」？

看 `TSigningSubjectServiceImpl.java:193-203`：删除时先 `publishEvent(new DataDeleteEvent(...))` 通知别的模块「这个主体被删了」，再 `deleteBatchIds(ids)`。

- **逻辑删除**：`del_flag` 打标记（见第 0 章 §4.6），数据还在库里。为什么？因为主体可能已经被合同引用了，物理删除会让历史合同「查不到主体」。**保留数据 = 保留可追溯性。**
- **发事件通知下游**：主体被删/停用了，可能影响别的模块（比如某个待审批的合同引用了它）。用 Spring 事件解耦，删除方不用知道「谁在关心这件事」。事件在 **第 6 章**会讲透，这里先认识。

### 4.2 第二步：Entity（对应表）

文件：`zxcm-contract/src/main/java/com/ruoyi/conf/domain/TSigningSubject.java`（答案册 `:37` 起）

你照着敲的骨架：

```java
package com.ruoyi.conf.domain;

import com.baomidou.mybatisplus.annotation.TableId;
import com.baomidou.mybatisplus.annotation.TableLogic;
import com.baomidou.mybatisplus.annotation.TableName;
import com.ruoyi.common.core.domain.BaseEntity;
import lombok.Data;
import lombok.EqualsAndHashCode;

@Data
@EqualsAndHashCode(callSuper = true)
@TableName("conf_signing_subject")        // ← 告诉 MyBatis-Plus 这张类对应哪张表
public class TSigningSubject extends BaseEntity {   // ← 白得 create_by/create_time 等 4 字段

    private static final long serialVersionUID = 1L;

    @TableId(value = "id")                // ← 主键；id 生成策略由全局配置 ASSIGN_ID 决定（雪花）
    private String id;

    private String signingSubjectCode;    // 签约主体编号
    private String signingSubjectName;    // 签约主体名称
    private String businessStatus;        // 企业经营状态
    private String uscc;                  // 统一社会信用代码

    @TableLogic                           // ← 逻辑删除标记字段
    private String delFlag;

    private String remarks;
    private String tenantId;
    private String status = "0";
    private String legalPersonName;
    private String legalPersonIdCard;
    private Date businessStartDate;
    private Date businessEndDate;
    private Integer forever = 0;          // 1=长期
    private String registeredCapital;
    private String tel;
    private String fax;
    private String areaCode;
    private String areaName;
    private String address;

    @Size(min = 0, max = 4000, message = "银行信息过多，请不要填写过多的银行信息")
    private String bankJson;               // 银行信息，JSON 数组字符串

    @Size(min = 0, max = 4000, message = "联系人信息过多，请不要填写过多的联系人")
    private String contacts;               // 联系人，JSON 数组字符串
}
```

**三个注解看仔细**（后面所有 Entity 都一样）：
1. `@TableName("conf_signing_subject")` —— 类 ↔ 表 的映射。注意类名去掉了 `T` 前缀，但表名带 `conf_` 前缀，靠注解对上。
2. `@TableId(value = "id")` —— 标明主键列。`idType` 没写，所以走全局的 `ASSIGN_ID`（雪花）。
3. `@TableLogic` —— 这个字段是逻辑删除标记。从此 `deleteBatchIds()` 自动变成 `update ... set del_flag=2`，查询自动带 `where del_flag=0`。

> ⚠️ **一个小坑**：Entity 的注释写的是「签约主体对象 **t_signing_subject**」（`:29`），但实际表名是 `conf_signing_subject`。**以获得 `@TableName` 注解为准**——这是 RuoYi 代码生成器留下的历史注释，别被误导。这也是我为什么强调「表名以注解为准」。

### 4.3 第三步：BO 和 VO

**BO**（接收前端参数）：`zxcm-contract/src/main/java/com/ruoyi/conf/domain/bo/TSigningSubjectBo.java:40` 起。它和 Entity 字段几乎一样，**多了两样东西**：

```java
@Data
@EqualsAndHashCode(callSuper = true)
@ApiModel("签约主体业务对象")
public class TSigningSubjectBo extends BaseEntity {

    @NotBlank(message = "主键不能为空", groups = {EditGroup.class})   // ← 分组校验
    private String id;

    @NotBlank(message = "签约主体名称不能为空", groups = {AddGroup.class, EditGroup.class})
    private String signingSubjectName;

    @NotBlank(message = "统一社会信用代码不能为空", groups = {AddGroup.class, EditGroup.class})
    private String uscc;

    @JsonFormat(pattern = "yyyy-MM-dd")     // ← 日期格式，前端传 "2024-01-01"
    private Date businessStartDate;
    // ... 其余字段
}
```

**关键在 `groups = {...}`**（`TSigningSubjectBo.java:46/61/74`）：
- `id` 只在 **EditGroup**（修改）时必填 —— 新增时当然没有 id；
- 名称、信用代码在 **两个组**都必填。

前端校验只能拦住「正常用户」，**后端的 `@Validated` 才是真正的防线**。分组校验让「新增」和「修改」能用同一个 BO 却有两套规则。

**VO**（返回给前端）：`zxcm-contract/src/main/java/com/ruoyi/conf/domain/vo/TSigningSubjectVo.java:37` 起。差别在于：
- 多了 `private Boolean disabled;`（`:88`）—— 这是给前端开关用的**计算字段**，表里没有；
- 带了一堆 `@ExcelProperty` 注解（`:44/51/...`）—— 用来做 Excel 导出，给字段起「中文列名」；
- `businessStatus` 上标了 `@ExcelDictFormat(dictType = "business_status")`（`:66`）—— 导出 Excel 时把字典值（比如 `1`）翻译成中文（比如 `正常`）。

**为什么 VO 和 Entity 不能合并？** 因为 VO 要装「表里没有的字段」（`disabled`），要控制「哪些字段导出 Excel」，还要能「藏字段」。Entity 只管数据库，不能干这些。

```java
private LambdaQueryWrapper<TSigningSubject> buildQueryWrapper(TSigningSubjectBo bo) {
    LambdaQueryWrapper<TSigningSubject> lqw = Wrappers.lambdaQuery();
    lqw.eq(StringUtils.isNotBlank(bo.getSigningSubjectCode()), TSigningSubject::getSigningSubjectCode,
           bo.getSigningSubjectCode());
    lqw.like(StringUtils.isNotBlank(bo.getSigningSubjectName()), TSigningSubject::getSigningSubjectName,
             bo.getSigningSubjectName());
    lqw.orderByDesc(TSigningSubject::getCreateTime);
```

这个写法有个**很容易被面试问到的技巧**：`eq(条件, 字段, 值)` 的**第一个参数是布尔「条件」**——`StringUtils.isNotBlank(...)` 为 `true` 时才拼这段 `where`。所以前端没传「主体编号」，这一段就**不会**进 SQL。这是 MyBatis-Plus 条件构造器的「**动态拼接**」写法，比在 XML 里写一堆 `<if test="...">` 干净得多。

**逐行读：`insertByBo` 这 8 行分别在做什么**

| 行 | 代码 | 在干什么 | 为什么这么写 |
|---|---|---|---|
| 1 | `BeanUtil.toBean(bo, TSigningSubject.class)` | 把 BO 按属性名拷成 Entity | 前端表单对象和后端表对象分开，靠拷贝桥接；属性名对不上的字段不会被赋值 |
| 2 | `if (add.getForever() == 1)` | 判断是不是「长期」主体 | 长期主体不需要结束日期 |
| 3 | `add.setBusinessEndDate(null)` | 把结束日期清空 | 避免旧值残留，和前端「长期」开关保持一致 |
| 4 | `validEntityBeforeSave(add)` | 保存前做名称唯一性校验 | 业务规则放 Service，Controller 不碰；新增和修改共用这一段 |
| 5 | `add.setCreateBy("admin"); add.setUpdateBy("admin")` | 手动写创建人/更新人 | **历史遗留**：正常应由 `BaseEntity` 的自动填充完成（见下方坦白点） |
| 6 | `baseMapper.insert(add) > 0` | 执行插入，返回影响行数 | MyBatis-Plus 自动生成 INSERT SQL，并生成雪花 ID |
| 7 | `bo.setId(add.getId())` | 把刚生成的 id 回填给 BO | 前端后续修改需要知道新记录的 id |
| 8 | `return flag` | 返回成功/失败 | Controller 用 `toAjax` 把它转成 `R.ok()` / `R.fail()` |

> ⚠️ **两个「坦白点」**（面试时能主动说出来会显得你真读过代码）：
> 1. `setCreateBy("admin")` 是**硬编码**的，没走第 0 章讲的「自动填充」。正常情况下应该靠 `BaseEntity` 的 `@TableField(fill = FieldFill.INSERT)` 自动填当前登录人，这里是历史遗留。
> 2. `add.getForever() == 1` 里 `forever` 是 `Integer`，和 `1` 比较——如果是 `null` 这里会 NPE。属于可以改进的地方（用 `Integer.valueOf(1).equals(...)` 或先判空）。

#### 4.6.1 完整链路

```
① 用户登录
```

#### 4.6.2 三个必须记住的点

1. **Token 是本项目用了 JWT 风格的**（`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/config/SaTokenConfig.java:82-86` 的 `StpLogicJwtForStyle`）。注意别误解：这里 JWT 里主要带的是登录标识，**完整的 `LoginUser`（含权限列表、角色列表）存在 Sa-Token 的 token session 里**；`LoginHelper.getLoginUser()` 先读 ThreadLocal，再读 `StpUtil.getTokenSession()`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/helper/LoginHelper.java:94-100`），所以每次请求也不用查数据库。代价是 token session 的数据在服务端，集群部署时依赖 Redis 做共享。
2. **权限码不是硬编码在代码里的**，而是**存在数据库 `sys_menu` 表的 `perms` 字段**里。管理员在「菜单管理」里给菜单/按钮配 `perms`，再通过「角色」把这些权限分配给用户。**代码里的 `@SaCheckPermission("conf:signingSubject:add")` 就是去跟 `sys_menu.perms` 里的字符串比对。**
3. **前端 `v-hasPermi` 和后端 `@SaCheckPermission` 是两套**：前者（`hasPermi.js:9`）只是**把没权限的按钮从页面删掉**（好看、友好），**真正的拦截靠后端**。前端删按钮**不是**安全措施——用户可以直接调接口。所以**每个接口都必须有 `@SaCheckPermission`**。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：一个标准的增删改查功能，你们后端要写几个文件？各自职责？**

五件套：Controller（接口）+ Service 接口 + Service 实现（业务）+ Mapper（数据）+ Entity（表映射），外加 BO（入参）、VO（出参）。
**为什么这么拆**：Controller 只接请求、Service 管业务和事务、Mapper 只管 SQL，职责单一，改动隔离。（指 `zxcm-contract/src/main/java/com/ruoyi/conf/controller/TSigningSubjectController.java:77`、`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:55`）

**Q2：新增和修改为什么共用一个 BO？怎么区分校验规则？**

用 **JSR-303 分组校验**。BO 上的 `@NotBlank(groups = {EditGroup.class})` 表示「只在修改时必填」。Controller 新增时写 `@Validated(AddGroup.class)`、修改时写 `@Validated(EditGroup.class)`，同一套注解跑出两组规则。（指 `zxcm-contract/src/main/java/com/ruoyi/conf/domain/bo/TSigningSubjectBo.java:46` + `zxcm-contract/src/main/java/com/ruoyi/conf/controller/TSigningSubjectController.java:148/160`）
**追问：前端 `rules` 也校验了，后端为什么还要校验？** 前端校验是体验（即时提示、少发无效请求），可以被 Postman 或改代码绕过；后端 `@Validated` 才是最终防线（`TSigningSubjectController.java:148`、`:160`）。

**Q3：为什么返回前端的不是 Entity 而是 VO？**

因为返回数据经常要**加工或裁剪**。本项目在列表接口里**现场给每条数据拼了一个「默认联系人（当前登录人）」**（`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:83-95`），这个字段数据库里没有，必须用 VO 装。

**Q4：Sa-Token 的 `@SaCheckPermission` 是怎么生效的？权限码从哪来？**

Sa-Token 注册了两个拦截器（`SaTokenConfig.java:52-80`）：`SaRouteInterceptor` 统一做登录校验，`SaAnnotationInterceptor` 扫描 `@SaCheckPermission` 做权限校验。权限校验时会回调 `StpInterface` 实现 `SaInterfaceImpl`，它返回当前登录用户的权限列表（`SaInterfaceImpl.java:29-38`）。
**权限码不存在代码里，存在数据库** `sys_menu.perms` 字段，通过「角色」分配给用户。登录时算好缓存起来。

**Q5：前端按钮权限已经隐藏了，后端还需要校验吗？**

**必须要。** 前端的 `v-hasPermi`（`hasPermi.js:9`）只是「把没权限的按钮从页面删掉」，是**体验优化，不是安全措施**——用户完全可以绕过前端直接调接口。所以每个接口都必须有后端 `@SaCheckPermission`。

**Q6：你们的一个「检索」接口，为什么写了「最少 4 个字、结果不能超过 1 条」这种逻辑？**

这是**接口级的越权/刷数据防护**。该接口是半公开的，为了防止无权限用户批量拉取公司主体信息，做了数据暴露面的限制：搜索词太短（太宽泛）、结果太多（像批量导出）、结果为空（像在探测）都直接拒绝，只有「精确定位到 1 家」才返回。（指 `TSigningSubjectController.java:94-116`）

**Q7：删除了一个签约主体，数据库里数据还在吗？为什么？**

还在，是**逻辑删除**。`del_flag` 字段标了 `@TableLogic`，删除只把 `del_flag` 改成 2，查询自动加 `where del_flag=0`。原因是**主体可能已被历史合同引用**，物理删除会让合同查不到主体、破坏可追溯性。
**追问：逻辑删除的数据越积越多，会不会拖慢查询？** 会。框架自动加的 `where del_flag=0` 若走不到合适索引，会扫更多行。本项目 `conf_signing_subject` 的 DDL 只有主键索引（`E:/Develop/project/zxcm-learn/script/sql/04-biz-tables.sql:39-67`），数据量大时应补 `(del_flag, create_time)` 这类联合索引。

**Q8：一个主体有多个银行账号和联系人，你们怎么存？为什么不建子表？**

存成 **JSON 字符串**放在主表字段里（`bankJson`、`contacts`）。不建子表是因为这两类数据**永远跟着主体一起读写、从不独立查询**，建子表的成本大于收益。如果将来有「按联系人检索」的需求，再迁移成子表。（指 `zxcm-contract/src/main/java/com/ruoyi/conf/domain/TSigningSubject.java:123` 的 `bankJson`、`:129` 的 `contacts`）

**Q9：删除时发了个 `DataDeleteEvent`，这是干嘛的？**

用 **Spring 事件**通知下游解耦。主体被删可能影响其他模块（比如引用了它的合同），发布事件后由关心方自己监听处理，删除逻辑不需要知道「谁在关心」。（详见第 6 章）

**Q10：新增时有没有可能产生重复数据？怎么防？**

两层：① 业务层 `validEntityBeforeSave` 查重（只有名称查重，信用代码查重被注释掉了 —— `zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:171-173`）；② 接口层 `@RepeatSubmit` 防「用户手抖点两次」。**注意业务唯一性只靠代码查，数据库没有加唯一索引**——这是个可以改进点（并发下仍可能插入重复）。

### 本章答辩卡（3 组追问级问答）

**卡片 1：`BeanUtil.toBean(bo, Entity.class)` 拷贝时，如果 BO 和 Entity 的字段名不一致会怎样？**

> **10 秒答案**：Hutool 的 `BeanUtil` 按属性名拷贝，名字对不上的字段不会被赋值，也不会报错；所以 BO、Entity、VO 的字段名必须保持一致。VO 转换同理，由 `BaseMapperPlus` 内部按属性名复制。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:133`（`BeanUtil.toBean`），`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/mapper/BaseMapperPlus.java:238`（`BeanCopyUtils.copyList` 转 VO）。

**卡片 2：`insertByBo` 和 `deleteWithValidByIds` 都没有 `@Transactional`，会不会有问题？**

> **10 秒答案**：新增是「先查重 SELECT、再 INSERT」两条语句，删除是「先发事件、再删数据」两条语句，都没有显式事务；单条 SQL 本身原子，但多步组合在并发下存在窗口（比如查重后、插入前别人也插了同名）。规范做法是加事务，或用数据库唯一索引兜底。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:131-145`（新增，无事务注解）、`:193-203`（先 `publishEvent` 再 `deleteBatchIds`）。

**卡片 3：Mapper 里为什么单独写了一条 `updateSetDateNull` 的 SQL？直接用 `updateById` 把结束日期设成 null 不行吗？**

> **10 秒答案**：不行。项目把 MyBatis-Plus 的 `updateStrategy` 配成了 `NOT_NULL`，`updateById` 会跳过值为 null 的字段，`setBusinessEndDate(null)` 根本不会进 SQL。所以「长期主体要清空结束日期」只能手写一条 `@Update` SQL。
> **证据**：`ruoyi-admin/src/main/resources/application.yml:259-261`（`updateStrategy: NOT_NULL`）、`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TSigningSubjectServiceImpl.java:155-157`（调用手写方法）、`zxcm-contract/src/main/java/com/ruoyi/conf/mapper/TSigningSubjectMapper.java:34-35`（`@Update` SQL）。

## 七、选型对比：为什么不选其他技术栈

### 7.1 鉴权框架：为什么用 Sa-Token，不用 Spring Security / Shiro？

| 方案 | 优点 | 本项目的顾虑 |
|---|---|---|
| Spring Security | 生态强大、企业最主流 | 配置重、概念多（FilterChain、UserDetailsService…），对「后台管理系统」这种场景**过度设计** |
| Shiro | 轻量、老牌 | 和 Spring Boot 结合不如 Sa-Token 顺 |
| **Sa-Token（选用）** | **API 极简**（`StpUtil.login()`、`@SaCheckPermission`），注解式鉴权，开箱即用 | 生态比 Spring Security 小 |

**结论**：合同系统是「**典型后台管理系统**」，要的是「登录 + 菜单权限 + 按钮权限」，Sa-Token 用最少代码搞定这些。若是有「OAuth2 授权服务器、微服务网关鉴权」这类复杂需求的系统，才轮到 Spring Security。

### 7.2 权限模型：为什么用「RBAC（角色-权限）」而不是「直接给用户配权限」？

项目里权限是通过「**用户 → 角色 → 菜单/按钮权限**」三层关联的（`sys_user` / `sys_role` / `sys_menu` / `sys_role_menu`）。为什么不直接给用户挂权限？因为**公司里同一岗位的人权限是一样的**——给角色配一次，一百个同岗位用户自动生效；直接给用户配，一百个人配一百遍。**RBAC 的核心价值是「权限的复用和维护成本」。**

### 7.3 一对多数据：为什么用 JSON 字符串，不用子表？

见 §2.2。核心判断：**「有没有独立查询需求」**。没有 → JSON 字符串最省事；有 → 老老实实建子表。这题的本质是「**别为不存在的需求过度设计**」。

### 7.4 主键：为什么是雪花 ID 的 varchar，不是自增 int？

见第 0 章 §7.3。补一句本项目的具体理由：合同系统数据量会一直增长，且未来可能分库；自增 ID 在分库时会撞号，雪花 ID 不会。

### 7.5 防重复提交：为什么用 `@RepeatSubmit` 注解 + Redis，不在前端拦？

前端拦（点完按钮置灰）**拦不住「刷新页面后重发」「用 Postman 直接打接口」**。防重提交必须做在服务端：`@RepeatSubmit` 用 Redis 记录「这个用户最近 N 秒发过这个请求」，重复就拒。前端置灰只是**体验**，服务端防重才是**安全网**。
