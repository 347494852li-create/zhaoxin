# 第 2 章 · 合作方管理

> 第 1 章的签约主体是「**我方**」，本章的合作方（也叫「相对方」）是「**对方**」——你签合同的另一家公司。
>
> 表面上看，它和第 1 章几乎一样（又是增删改查），但多了**一整章最该学会的东西——数据权限**。第 1 章所有用户看到的是同一份主体列表；本章不一样：**每个人看到哪些合作方，取决于他是谁、他负责哪些**。
>
> **本章第一次讲透**：① `@DataPermission` 数据权限（**注意：它标在 Mapper 上，不在 Controller**）；② 「数据权限的开关值藏在 `sys_role` 角色表里」这个反直觉设计；③ 一个**更新接口里为什么还要再做一次权限校验**。
>
> **本章你会碰到的表**：`conf_contract_counterpart`（业务主表）+ `sys_role`（**数据权限的配置源**）+ `sys_user`（查负责人姓名）+ 第 1 章认识的框架表。

> **零基础先补概念（本章的三个新词）**
>
> - **功能权限**：能不能「进这个门、调这个接口」。例如有没有 `conf:contractCounterpart:list` 这个权限码，靠 `@SaCheckPermission` 判断（写法见第 1 章 §4.6）。它管的是「接口级」的准入。
> - **数据权限**：进了门之后，能看见「哪些行」。例如同样调列表接口，普通业务员只看到自己负责的合作方，主管能看到整个部门。它管的是「行级」的过滤，本章用 `@DataPermission` 实现。
> - **SpEL 模板 + 反射**：本项目把「数据范围规则」写成带占位符的 SQL 模板（比如 `#{#userId} = #{#user.userId}`），运行时用 Spring 表达式（SpEL）求值；角色配置存在 `sys_role` 的某一列里，用反射按枚举名读出来。听不懂没关系，§2.3~§2.4 会拆开讲。

## 一、这部分是做什么的？

### 1.1 业务含义

**合作方 = 合同里的另一方**。比如你（签约主体：山西肇新）要和「某某科技公司」签合同，「某某科技公司」就是合作方。它的信息和签约主体几乎对称：名称、信用代码、法人、经营状态、银行账号、联系人……**外加一个关键字段：负责人**。

### 1.2 和第 1 章最大的区别：多了「负责人」和「数据权限」

| | 签约主体（第 1 章） | 合作方（本章） |
|---|---|---|
| 谁能看 | 有 `conf:signingSubject:*` 权限的人 **全部都能看** | 有权限还不够，**还得是这个合作方的「相关负责人」才能看** |
| 关键字段 | 无 | **`CONTRACT_COUNTERPART_HEAD`（负责人）** ← 数据权限的「锚点」 |

**这就是「功能权限」和「数据权限」的区别**，一定要分清：

- **功能权限（第 1 章学的）**：你能不能**进这个门**——能不能调「合作方列表」这个接口。靠 `@SaCheckPermission("conf:contractCounterpart:list")`。
- **数据权限（本章学的）**：进了门之后，你能不能**看到里面所有的东西**——还是只能看到属于你的那一部分。靠 `@DataPermission`。

现实里为什么需要数据权限？因为公司有 100 个业务员、10 万个合作方。如果每个业务员都能看到全部合作方，那是信息泄露、也是干扰（他只想看自己负责的）。**数据权限 = 「按归属过滤行」。**

### 1.3 本章接口

| 接口 | 干什么 | 有数据权限吗 |
|---|---|---|
| `GET /conf/contractCounterpart/list` | 分页列表 | ✅ 有（只能看你负责的） |
| `GET /conf/contractCounterpart/{id}` | 查详情 | ❌ 没有（按 ID 直接查） |
| `POST /conf/contractCounterpart` | 新增 | —— |
| `PUT /conf/contractCounterpart` | 修改 | ✅ **方法体内手工校验**（§5.4） |
| `PUT /conf/contractCounterpart/changeStatus` | 改状态 | —— |
| `DELETE /conf/contractCounterpart/{ids}` | 删除 | ❌ 没有 |
| `POST /conf/contractCounterpart/export` | 导出（复杂合并单元格） | ✅ 有 |
| `POST /conf/contractCounterpart/importData` | Excel 导入 | —— |
| `GET /conf/contractCounterpart/hide` `/show` | 隐藏/显示「个人」合作方 | —— |

## 二、站在架构师 / 开发经理角度：为什么这么设计？

### 2.1 为什么「数据权限」要放在 Mapper 层（SQL 层）拦截，而不是在 Service 里过滤？

这是本章最核心的设计判断。有两种做法：

**做法 A（在 Service 里过滤）**：查出来全部，再在 Java 里 `if (数据不属于我) 跳过`。
**做法 B（在 SQL 里过滤，本项目选的）**：给 SQL **默默加上一个 `where` 条件**，数据库只返回该返回的行。

| | A：Service 里过滤 | **B：SQL 层过滤（选用）** |
|---|---|---|
| 性能 | 差——**先把全部数据捞进内存再丢掉**，10 万条数据只留 10 条也得查 10 万条 | 好——数据库直接只查 10 条 |
| 分页 | **会错**——第 1 页 10 条里可能 9 条被你过滤掉，变成只显示 1 条 | 正确——过滤发生在分页之前 |
| 安全 | 全靠程序员记得写过滤，**漏一个地方就是漏洞** | 在 SQL 层统一拦截，**标注解就生效** |
| 代码 | 每个查询方法都要手写过滤 | 一个注解搞定 |

**分页正确性这一条是决定性的**。做法 A 会让「每页 10 条」变成「每页 0~10 条随机数」，用户以为数据丢了。

所以本项目的方案是：**用 MyBatis-Plus 的插件机制，在 SQL 执行前偷偷改 SQL**（`PlusDataPermissionInterceptor` + `PlusDataPermissionHandler`）。你只要在 Mapper 方法上标个 `@DataPermission`，框架就自动帮你的 SQL 加上过滤条件。

### 2.2 为什么 `@DataPermission` 标在 **Mapper** 上，不标在 Controller/Service 上？

因为**拦截点在 SQL 生成的那一刻**。数据权限的实现是「改写 SQL 的 `where` 子句」，这件事只有**在 Mapper 执行 SQL 时**才做得到。

- 标的**位置**：Mapper 接口的**方法**上（`zxcm-contract/src/main/java/com/ruoyi/conf/mapper/TContractCounterpartMapper.java:46/54/60`）
- 标的**内容**：告诉框架两件事——
  1. `@DataColumn(key="userId", value="a.contract_counterpart_head")` → **拿哪个字段跟当前用户比**（这里是「负责人」字段）
  2. `resource = DataPermissionResource.partnerPermission` → **去角色的哪个列里读权限配置**（§2.3）

**这是反直觉的**——新手会以为「权限」应该标在接口（Controller）上。记住：**功能权限标 Controller（`@SaCheckPermission`），数据权限标 Mapper（`@DataPermission`）**。

### 2.3 最反直觉的设计：数据权限的「开关值」为什么存在 `sys_role` 角色表里？

RuoYi-Vue-Plus 原生的数据权限只有**一个**开关——`sys_role.data_scope`（一个角色一种数据范围，字段在 `ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysRole.java:87`）。但本合同系统有**十个业务域**，每个域的数据权限需要**独立配置**：

- 合同草拟数据的权限（`draftPermission`）
- 审批完成的合同权限（`contractPermission`）
- 台账权限（`ledgerPermission`）
- 用印权限（`stampPermission`）
- **相对方数据权限（`partnerPermission`）** ← 本章这个
- ……连同默认的 `base` 一共 11 项，其中业务域 10 个（见 `ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:22-32`）

**所以本项目给 `sys_role` 表加了一整排列**——一个业务域一列，共 10 列（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysRole.java:144-153`：`draftPermission` / `contractPermission` / … / `partnerPermission` / `workPermission`）。每个角色在每一列上配一个「数据范围代码」。

`DataPermissionResource` 枚举（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:16`）里那句注释说得最清楚：

```java
/**
 * 使用说明，这里的index需要和role表的字段名一一对应。
 * 系统会使用泛型的方式去读取当前角色配置的权限范围.
 */
partnerPermission("partnerPermission", "相对方数据权限"),
```

**「index 和 role 表的字段名一一对应」**——枚举名 `partnerPermission` 就是 `sys_role` 的**列名**，也是 `RoleDTO` 的**字段名**（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/dto/RoleDTO.java:59`）。框架用**反射**（`ReflectUtil.getFieldValue(role, resource.getIndex())`，见 `ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:141`）按这个字符串去角色对象里取值。**加一个新业务域的数据权限 = 加一个枚举 + 加一个列**，这是一种「用命名约定换灵活扩展」的设计。

> **面试怎么答**：「RuoYi 原生数据权限只有一个 `data_scope`，我们系统有十个业务域需要独立的数据权限，所以扩展成『一个业务域一个角色列』，用枚举名和列名一一对应 + 反射读取。好处是加业务域只改配置不动框架代码。」

### 2.4 权限值（1~7）到底代表什么？为什么用「SpEL 模板」而不是 if-else？

每个角色在 `partnerPermission` 列里存一个数字代码，含义定义在 `ContractPermission` 枚举（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/ContractPermission.java:31`）：

| 代码 | 含义 | 生成的 SQL 片段（`sqlTemplate`） |
|---|---|---|
| `1` | 全部数据 | **空**（不过滤） |
| `2` | 自定义 | `1=0`（默认不给） |
| `3` | 本部门 | `#{#userId} IN #{@sdss.getDeptUser(#user)}` |
| `4` | 本部门及以下 | `#{#userId} IN (#{@sdss.getDeptAndChildUser(#user)})` |
| `5` | 仅本人 | `#{#userId} = #{#user.userId}` |
| `6` | 我管理的部门 | `#{#userId} IN (#{@sdss.getMyDeptUser(#user)})` |
| `7` | 我管理的部门及以下 | `#{#userId} IN (#{@sdss.getMyDeptAndChildUser(#user)})` |

**为什么用 SpEL 模板而不是一堆 `switch-case` 拼字符串？** 因为这段 SQL 片段里**要嵌入动态计算**：`#{@sdss.getDeptUser(#user)}` 是**运行时调用一个 Spring Bean（`@sdss`）算出「你的部门下所有用户 ID」**。用 SpEL 模板，SQL 片段和「动态求值」写在了一起，加新规则只需加一行枚举，不用改任何 Java 逻辑。这是「**配置化 > 硬编码**」的典型。

最终拼出来的 SQL 长这样（假设某角色是「仅本人」，用户 ID 是 100）：

```sql
SELECT * FROM conf_contract_counterpart
WHERE (del_flag='0' ... 你原本的条件 ...)
  AND (a.contract_counterpart_head = 100)     -- ← @DataPermission 自动加上去的
```

### 2.5 为什么「查询」用 `OR` 拼、而「更新/删除」用 `AND` 拼？

看 `PlusDataPermissionHandler.java:126`：

```java
// 更新或删除需满足所有条件
String joinStr = isSelect ? " OR " : " AND ";
```

- **查询**：一个人可能有**多个角色**，每个角色给一份数据范围。查询时「只要满足**任意一个**角色给的范围就能看」→ 用 `OR` 并起来（宽松，好看全）。
- **更新/删除**：必须**所有角色都允许**才准动这条数据 → 用 `AND`（严格，除非人人都有权，否则不许改）。

**这是「读宽松、写严格」的安全原则**。面试被问「多角色时数据权限怎么合并」，这个细节很加分。

**① 列表查询「带权限」的写法（`:96-101`）**

```java
@Override
public TableDataInfo<TContractCounterpartVo> queryPermissionPageList(TContractCounterpartBo bo,
    PageQuery pageQuery) {
    LambdaQueryWrapper<TContractCounterpart> lqw = buildQueryWrapper(bo);
    Page<TContractCounterpartVo> result = baseMapper.selectPagePartnerByPermission(pageQuery.build(), lqw);
    //                                     ↑ 注意：调的是 Mapper 里标了 @DataPermission 的方法

```

**关键**：它调用的**不是**白得的 `selectVoPage`，而是 Mapper 里**自己定义的 `selectPagePartnerByPermission`**（因为只有那个方法标了 `@DataPermission`，§4.6）。**「带权限查询」的秘密全在「调用哪个 Mapper 方法」上。**

**② 修改里「手工再做一次权限校验」（`:184-195`）** —— 这是个值得琢磨的点：

```java
@Override
public Boolean updateByBo(TContractCounterpartBo bo) {
    TContractCounterpart update = BeanUtil.toBean(bo, TContractCounterpart.class);
    TContractCounterpart contractCounterpart = baseMapper.selectById(bo.getId());

    // 查询判断是否有权限修改
    LambdaQueryWrapper<TContractCounterpart> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(TContractCounterpart::getId, bo.getId());
    List<TContractCounterpart> pData = this.baseMapper.selectPartnerByPermission(wrapper);   // ← 带权限查一次
    if (pData.size() == 0) {
        throw new ServiceException("您没有权限操作该数据");     // 查不到 = 你没权看这条 = 不许改
    }
    // ... 后续更新逻辑
}
```

**逐行读：这段「手工数据权限校验」在防什么**

| 行 | 代码 | 在干什么 | 为什么这么写 |
|---|---|---|---|
| 1 | `BeanUtil.toBean(bo, TContractCounterpart.class)` | 把前端提交的 BO 拷成待更新的 Entity | 后续 `updateById` 需要 Entity |
| 2 | `baseMapper.selectById(bo.getId())` | 按 ID 取出**旧数据** | 后面 `CompareUtils` 要拿旧值和新值做对比、记录变更；注意这个调用**不带数据权限** |
| 3 | `wrapper.eq(TContractCounterpart::getId, bo.getId())` | 构造「只查这一条」的条件 | 精确到主键，避免全表 |
| 4 | `this.baseMapper.selectPartnerByPermission(wrapper)` | **用带 `@DataPermission` 的方法再查一次** | 框架会在这个 SQL 上自动追加「负责人是我/我部门」的条件 |
| 5 | `if (pData.size() == 0) throw ...` | 带权限查不到 → 拒绝更新 | 防止「知道别人的 ID 就能改」；这是手工兜底，不是注解自动生效 |
| 6 | 后续 `updateById` | 真正更新 | 走到这里说明第 4 步已确认你有权 |

**为什么 `selectById` 之后还要再用「带权限的方法」查一次？** 因为 `selectById` 是**不带数据权限**的（它是 MyBatis-Plus 白得的方法，没标 `@DataPermission`）。所以**任何人只要知道 ID 就能查到这条数据**。

那怎么防「越权改别人负责的合作方」？办法就是：**再用「带权限的查询」查一次，查得到才说明你有权，查不到就抛异常**。

> **面试重点**：这体现了一个真实项目的「**数据权限不是自动全覆盖的**」——只有标了 `@DataPermission` 的方法才受保护。所以「按 ID 查详情」这类接口要么额外手工校验，要么接受「知道 ID 就能看」的风险。本项目 **`getInfo`（详情接口）就没做数据权限校验**（`zxcm-contract/src/main/java/com/ruoyi/conf/controller/TContractCounterpartController.java:283-286` 直接 `queryById`）——这是一个**可改进点/潜在越权风险**，面试如果被追问「数据权限是不是所有接口都有」，你答：「不是，只有查询列表和导出这类方法标了注解，按 ID 查详情没标，属于已知缺口。」

**③ 变更留痕（`:206-220`）** —— 修改时记录「改了哪些字段」：

```java
String result = new CompareUtils<TContractCounterpart>().compare(contractCounterpart, update);
JSONObject object = new JSONObject();
object.put("date", DateUtils.getDate());
object.put("userId", LoginHelper.getLoginUser().getUserId());
object.put("username", LoginHelper.getLoginUser().getNickName());
object.put("result", result);              // 比如 "名称: 旧→新; 电话: 旧→新"

    // 把这条变更记录 append 到 remarks 字段（JSON 数组）里
    update.setRemarks(array.toString());
}
```

**设计意图**：合作方信息变更频繁，谁改了什么都得留痕（审计要求）。做法是**把「变更历史」当成一个 JSON 数组，累积存在 `remarks` 字段里**——又是「一对多用 JSON 字符串」套路（第 1 章 §2.2）。好处是不建审计子表；代价是 `remarks` 会越滚越大、且无法按字段查询。

### 4.5 本章重点：`@DataPermission` 到底怎么写（第一次讲透）

**Mapper**：`zxcm-contract/src/main/java/com/ruoyi/conf/mapper/TContractCounterpartMapper.java:38` 起。

先看**没有**数据权限的普通方法（`:41-44`）：

```java
@Select("select a.*, b.NICK_NAME as headName "
      + "from CONF_CONTRACT_COUNTERPART a left join SYS_USER b on a.CONTRACT_COUNTERPART_HEAD = b.USER_ID "
      + "${ew.customSqlSegment}")
List<TContractCounterpartVo> getListJoinSysUser(@Param(Constants.WRAPPER) QueryWrapper<TContractCounterpart> lqw);
```
（`${ew.customSqlSegment}` 是 MyBatis-Plus 的「把条件构造器里的条件拼进来」占位符；`headName` 是 join `sys_user` 取到的负责人姓名。）

再看**有**数据权限的版本（`:46-52`）——**只多了一个注解**：

```java
@DataPermission(value = {@DataColumn(key = "userId", value = "a.contract_counterpart_head")},
    resource = DataPermissionResource.partnerPermission)
@Select("select a.*, b.NICK_NAME as headName "
      + "from CONF_CONTRACT_COUNTERPART a left join SYS_USER b on a.CONTRACT_COUNTERPART_HEAD = b.USER_ID "
      + "${ew.customSqlSegment}")
List<TContractCounterpartVo>
    getListJoinSysUserWithPermission(@Param(Constants.WRAPPER) QueryWrapper<TContractCounterpart> lqw);
```

**注解拆开读**：

```java
@DataPermission(
    // ① key = "userId"：告诉 SpEL 模板里的 #{#userId} 这个变量该填什么
    //    value = "a.contract_counterpart_head"：填的就是「哪一列是负责人」
    value = { @DataColumn(key = "userId", value = "a.contract_counterpart_head") },
    // ② 去角色的哪个列读权限配置（§2.3）
    resource = DataPermissionResource.partnerPermission
)
```

**对照 `ContractPermission.SELF` 的模板** `#{#userId} = #{#user.userId}`（`ContractPermission.java:56`）：
- `#{#userId}` ← 被替换成 `a.contract_counterpart_head`
- `#{#user.userId}` ← 被替换成当前登录用户的 ID（比如 `100`）

拼出来就是 `a.contract_counterpart_head = 100`。**「只有负责人是我」的合作方才查得出来。**

同一张 Mapper 里，`:54-58` 的 `selectPartnerByPermission` 和 `:60-64` 的 `selectPagePartnerByPermission` 都是同样的套路，只是返回值类型不同（List / Page）。

**注意 `a.` 前缀**：因为 SQL 里有 join，字段必须带表别名 `a.` 才不会歧义。所以 `@DataColumn` 的 `value` 写的是 `a.contract_counterpart_head` 而不是裸列名。

### 4.6 数据权限的执行链路（框架内部，理解即可）

你标好注解后，框架在 SQL 执行前做了什么？看 `PlusDataPermissionHandler.java:87` 的 `getSqlSegment`：

```
MyBatis-Plus 执行 SQL 前
  ↓
PlusDataPermissionInterceptor 拦下来        （MybatisPlusConfig 里注册的插件）
  ↓
PlusDataPermissionHandler.getSqlSegment(where, 方法ID, isSelect)   :87
  ├─ findAnnotation(方法ID)   :88 → 反射找出这个 Mapper 方法上的 @DataPermission
  │     没找到 → 记进「无效缓存」，直接返回原 where（等于不拦截，性能优化）

  ├─ 租户管理员 → 不过滤       :99
  ├─ buildDataFilter(...)     :102 → 算出要拼的 SQL 片段（见下）
  ├─ JSqlParser 把片段解析成表达式  :107
  └─ 用 AndExpression 挂到原 where 上  :111 → 返回改写后的条件
  ↓

```

`buildDataFilter`（`:123-197`）的算法：

```
joinStr = 查询 ? " OR " : " AND "              :126   ← §2.5 的读写差异
for (每个角色 role) {                            :137
    如果 resource != base（本项目大多走这条）：

```

> ⚠️ **一个值得注意的行为**：`:141-143` 里，如果某个角色的 `partnerPermission` 列是**空字符串**，代码直接 `return ""`——**整个数据权限就失效了（变成不过滤）**。而如果配的是一个**非法的代码**（比如 `"9"`），则会抛 `ServiceException("角色数据范围异常")`（`:147`）。也就是说「**没配 = 全放行，配错 = 报错**」——这是个容易踩的坑：**新角色忘了配 partnerPermission，这个角色的人就能看到全部合作方**。面试可以主动提这个风险点。

## 六、面试官高频问题 + 答案（企业级视角）

**Q1：功能权限和数据权限有什么区别？**

功能权限管「能不能调这个接口/进这个页面」（`@SaCheckPermission`，标 Controller 方法）；数据权限管「能操作/看到哪些行数据」（`@DataPermission`，标 Mapper 方法）。
**举例**：合作方列表接口，能不能调是功能权限；调了之后只能看到「负责人是我」的记录，是数据权限。

**Q2：你们的数据权限是怎么实现的？**

用 MyBatis-Plus 的插件机制在 **SQL 层**拦截。在 Mapper 方法上标 `@DataPermission`，框架在 SQL 执行前用 JSqlParser 把数据权限的条件 `AND` 到原来的 `where` 上（`PlusDataPermissionHandler.java:87`）。
**为什么在 SQL 层**：① 分页正确（过滤在分页前）；② 性能好（数据库只查该查的）；③ 统一拦截，不容易漏。

**Q3：数据权限的配置存在哪？为什么存在角色表里？**

存在 `sys_role` 表里，而且**一个业务域一列**（`partnerPermission` / `draftPermission` / `ledgerPermission`… 共 10 列，`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysRole.java:144-153`）。
**为什么**：RuoYi 原生只有 `data_scope` 一个开关，但本合同系统有十几个业务域需要独立的数据权限配置。用「枚举名 ↔ 列名一一对应」（`DataPermissionResource.java:16`）+ 反射读取（`PlusDataPermissionHandler.java:141`）实现，加业务域只加枚举和列，不动框架代码。

**Q4：数据范围代码 1~7 是什么？怎么变成 SQL 的？**

1 全部 / 2 自定义 / 3 本部门 / 4 本部门及以下 / 5 仅本人 / 6 我管理的部门 / 7 我管理的部门及以下。定义在 `ContractPermission.java:31`，每个代码配一个 **SpEL 模板**，比如「仅本人」是 `#{#userId} = #{#user.userId}`。运行时把 `#userId` 换成「负责人字段名」、`#user` 换成当前用户，求值成真实的 SQL 条件。用 SpEL 模板是为了**把「动态求值」写进配置**，加规则只需加一行枚举。

**Q5：一个用户有多个角色，数据权限怎么合并？**

查询时用 `OR` 把各角色的范围并起来（满足任一即可看）；更新/删除时用 `AND`（必须所有角色都允许才准动）——`PlusDataPermissionHandler.java:126`。**「读宽松、写严格」**。

**Q6：为什么有的地方数据权限是自动的，有的地方要手写校验？**

只有**标了 `@DataPermission` 的 Mapper 方法**才自动生效。本项目里只有「列表查询」「导出」这类自定义方法标了注解；而「按 ID 查详情」「按 ID 更新」走的是 MyBatis-Plus 白得的 `selectById`/`updateById`（没标注解），所以：更新接口在 Service 里**手工**用带权限的方法查一次、查不到就抛「没权限操作」（`TContractCounterpartServiceImpl.java:190-195`）；而详情接口**没做**校验——这是已知缺口。
**追问：那按 ID 删除呢？** 同样没有数据权限保护。`deleteBatchIds` 是 MyBatis-Plus 白得的方法，当前代码只做了「禁止批量删除」和事件通知（`zxcm-contract/src/main/java/com/ruoyi/conf/service/impl/TContractCounterpartServiceImpl.java:269-278`），知道 ID 就能删。

**Q7：`@DataPermission` 为什么标在 Mapper 上，不标 Controller 上？**

因为拦截点是「SQL 生成的那一刻」。数据权限的实现就是改写 SQL 的 `where`，只有 Mapper 执行 SQL 时才能改。标 Controller 无法触及 SQL。
**追问：那能标在 Mapper 接口（类）上吗？** 可以。`@DataPermission` 的 `@Target` 包含 `TYPE`（`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataPermission.java:26`），框架也会查找类上的注解（`PlusDataPermissionHandler.java:224-229`）；但标在类上会作用到该 Mapper 的所有方法，方法级注解更精确。

**Q8：新增合作方时，`partnerPermission` 没配会怎样？**

`PlusDataPermissionHandler.java:141-143` 里，若角色该列为空字符串，直接 `return ""` → **数据权限失效，该角色用户能看到全部数据**。这是个容易踩的坑（配错则抛异常，漏配则全放行）。所以「新增角色时必须记得配数据权限」。

**Q9：复杂导出（合并单元格、一对多）你们怎么做？**

用 `EasyPoi` 的 `ExcelBuilder` 手工布局：先描述表头的多层合并单元格，再逐行按 `rowspan` 合并基本信息列、铺开多条银行/联系人（`TContractCounterpartController.java:113-249`）。简单扁平导出才用 `@ExcelProperty` 注解式。

**Q10：修改时怎么记录「谁改了什么」？**

用 `CompareUtils.compare(旧对象, 新对象)` 算出差异字符串，包成 JSON（含时间、改动人、改动内容），append 到 `remarks` 字段的 JSON 数组里（`TContractCounterpartServiceImpl.java:206-222`）。属于审计留痕，复用「一对多存 JSON 字符串」的套路。

### 本章答辩卡（3 组追问级问答）

**卡片 1：数据权限处理器是在哪一步拿到「当前用户有哪些角色」的？**

> **10 秒答案**：先从数据权限上下文或 `LoginHelper` 拿当前 `LoginUser`，然后遍历 `user.getRoles()`。每个角色再按注解里的 `resource` 枚举，用反射读出对应的权限列，逐个拼 SQL 片段。
> **证据**：`ruoyi-base/ruoyi-framework/src/main/java/com/ruoyi/framework/handler/PlusDataPermissionHandler.java:93-96`（取用户）、`:137`（遍历角色）、`:141`（反射读列）。

**卡片 2：Mapper 的 SQL 里做了表 join，`@DataColumn` 的字段名为什么必须带 `a.` 别名？**

> **10 秒答案**：因为 `CONF_CONTRACT_COUNTERPART` 和 `SYS_USER` 都有同名列（比如 ID、状态类字段），不带别名数据库无法判断 `contract_counterpart_head` 指哪张表，会报「column ambiguous」。所以注解里写 `a.contract_counterpart_head`。
> **证据**：`zxcm-contract/src/main/java/com/ruoyi/conf/mapper/TContractCounterpartMapper.java:41-43`（join 与别名 `a`）、`:46`（`value = "a.contract_counterpart_head"`）。

**卡片 3：如果新加一个业务域的数据权限，要改哪些地方？**

> **10 秒答案**：三处：① `DataPermissionResource` 加一个枚举（枚举名就是列名）；② `sys_role` 和 `SysRole`/`RoleDTO` 加同名列；③ 在目标 Mapper 方法上把 `resource` 指向新枚举。`PlusDataPermissionHandler` 不用改，因为它按枚举名反射取值。
> **证据**：`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/enums/permissionType/DataPermissionResource.java:22-32`、`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/entity/SysRole.java:143-153`、`ruoyi-base/ruoyi-common/src/main/java/com/ruoyi/common/core/domain/dto/RoleDTO.java:51-60`、`PlusDataPermissionHandler.java:141`。

## 七、选型对比：为什么不选其他技术栈

### 7.1 数据权限实现：为什么用「MyBatis-Plus 插件改写 SQL」，不用别的？

| 方案 | 问题 |
|---|---|
| Service 层查完再过滤 | **分页会错**、性能差、容易漏（§2.1） |
| 每个 SQL 手写 `where` | 重复、易漏，改规则要动所有 SQL |
| 数据库视图 / 行级安全（Row Level Security） | 复杂、跨库不通用、DBA 维护成本高 |
| **MyBatis-Plus 插件 + 注解（选用）** | **标一个注解就生效**、分页正确、统一拦截不易漏 |

**结论**：Java 生态里「SQL 层统一加过滤条件」最成熟的做法就是 MyBatis 的 Interceptor 机制，配套 JSqlParser 改写 SQL。

### 7.2 权限配置存储：为什么扩展 `sys_role` 加列，不新建「权限配置表」？

| 方案 | 评价 |
|---|---|
| 新建 `sys_role_data_permission(role_id, resource, scope)` 关联表 | 更「范式化」、加业务域不用改表结构 |
| **扩 `sys_role` 加列（选用）** | 查询快（不用 join）、和 RuoYi 原生 `data_scope` 风格一致，但**加业务域要 ALTER TABLE** |

**取舍**：本项目选了「简单直接、查询快」，代价是「加业务域要改表结构」。这是「**读多写少 + 业务域相对稳定**」场景下的合理选择——数据权限的读取是**每个查询都发生**的高频操作，加列比 join 快。若业务域会频繁变动，关联表方案更灵活。

### 7.3 多角色权限合并：为什么查询用 OR、写用 AND？

见 §2.5。本质是安全原则「**读可以宽松、写必须严格**」。如果写也用 OR，可能出现「A 角色允许改、B 角色不允许」时仍然放行的情况，违反最小权限。

### 7.4 变更留痕：为什么用 JSON 字符串存 `remarks`，不建审计表？

同第 1 章 §2.2 的逻辑——**没有独立查询需求**（谁会在 SQL 里按「变更内容」检索？），建审计表成本大于收益。缺点是 `remarks` 会膨胀、无 schema。适用于「低频、少量、只做展示」的留痕；如果是「高频、需要按操作人/时间检索」的审计，就该建正式审计表。

### 7.5 导出：为什么同时用「注解式」和「手工布局」两套？

不是二选一，而是**按复杂度分工**：扁平结构用 `@ExcelProperty`（省事）；需要合并单元格/一对多就用 `ExcelBuilder` 手工画（灵活）。**用一个工具解决所有场景**（要么都用注解，要么都手工）反而会让简单场景变复杂、或让复杂场景做不到。
