# 7.1 三层权限的总览

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：路由级                                            │
│  控制：能不能【打开】某个页面                                │
│  代码：permission.js + filterDynamicRoutes()                │
│  数据：sys_menu 表（后端按角色查出来的）                      │
│  类比：大楼门禁 —— 进不去就没法用                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  第 2 层：菜单级                                            │
│  控制：侧边栏【显示】哪些菜单                                │
│  代码：layout/components/Sidebar/*                          │
│  数据：sidebarRouters（来自 /getRouters，后端已筛过）         │
│  类比：楼层指示牌 —— 看不到入口不代表进不去                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  第 3 层：按钮级                                            │
│  控制：页面上【显示】哪个按钮                                │
│  代码：v-hasPermi 指令 → plugins/auth.js                    │
│  数据：permissions（来自 /getInfo）                          │
│  类比：房间里的开关 —— 藏起来不代表线路断了                   │
└─────────────────────────────────────────────────────────────┘
```

## ⭐ 三层的粒度对比

| 层 | 粒度 | 一个例子 |
|---|---|---|
| 路由级 | **页面级** | 能不能打开"合同草拟"页面 |
| 菜单级 | **可见性** | 侧边栏显示不显示"合同管理" |
| 按钮级 | **操作级** | "新增"按钮显示不显示 |

## ⭐ 三层的实现方式对比

| 层 | 在哪实现 | 怎么实现 |
|---|---|---|
| 路由级 | `permission.js` + `store/modules/permission.js` | 不把没权限的路由**注册**进去 |
| 菜单级 | **后端** `/getRouters` | 后端查表时**只返回有权限的** |
| 按钮级 | `directive/permission/hasPermi.js` | 没权限就把按钮**从 DOM 删掉** |

# 7.2 ⭐ 三个必须知道的真相

## 真相 1：前端几乎不"判断"权限，它只是"接收"权限

**很多人以为**：前端拿到"用户角色"和"所有菜单"，然后自己算"能看哪些"。

**实际是**：**后端直接告诉前端"你能看这些"**，前端只管显示。

### 证据：菜单是后端筛的

**位置**：`ruoyi-admin/src/main/java/com/ruoyi/web/controller/system/SysLoginController.java`

```java
@GetMapping("getRouters")
public R<List<RouterVo>> getRouters() {
    Long userId = LoginHelper.getUserId();
    List<SysMenu> menus = menuService.selectMenuTreeByUserId(userId);   // ★ 按 userId 查
    return R.ok(menuService.buildMenus(menus));
}
```

**`selectMenuTreeByUserId(userId)` 的 SQL 是什么样的？**

**大意是**：

```sql
SELECT DISTINCT m.*
FROM sys_menu m
LEFT JOIN sys_role_menu rm ON m.menu_id = rm.menu_id
LEFT JOIN sys_user_role ur ON rm.role_id = ur.role_id
WHERE ur.user_id = #{userId}
  AND m.menu_type IN ('M', 'C')      -- 只要目录和菜单，不要按钮
  AND m.status = 0                    -- 只要正常的
ORDER BY m.parent_id, m.order_num
```

**⭐ 所以后端返回的菜单树里，只有这个用户有权限的菜单。**
前端拿到什么就显示什么，**没有"过滤"这一步**。

### 证据：权限码也是后端给的

```java
// SysLoginController.getInfo()
Set<String> roles = permissionService.getRolePermission(user);      // 角色集合
Set<String> permissions = permissionService.getMenuPermission(user); // 权限码集合
ajax.put("user", user);
ajax.put("roles", roles);
ajax.put("permissions", permissions);
```

**位置**：`ruoyi-base/ruoyi-system/src/main/java/com/ruoyi/system/service/SysPermissionService.java`

```java
public Set<String> getRolePermission(SysUser user) {
    Set<String> roles = new HashSet<String>();
    if (user.isAdmin()) {
        roles.add("admin");                              // ★ 后端硬编码的超级角色
    } else {
        roles.addAll(roleService.selectRolePermissionByUserId(
            user.getUserId(), user.getTenantId()));
    }
    return roles;
}

public Set<String> getMenuPermission(SysUser user) {
    Set<String> perms = new HashSet<String>();
    if (user.isAdmin()) {
        perms.add("*:*:*");                              // ★ 后端硬编码的超级权限
    } else {
        perms.addAll(menuService.selectMenuPermsByUserId(
            user.getUserId(), user.getTenantId()));
    }
    return perms;
}
```

**⭐ 注意：`"*:*:*"` 和 `"admin"` 都是后端 Java 代码里硬编码的常量**，
不是数据库里配的。

**所以"admin 能看到所有按钮"这件事，是后端决定的，不是前端。**

## 真相 2：`*:*:*` 和 `admin` 是两个不同的通配符

**容易混，必须分清。**

| 通配符 | 属于 | 作用范围 | 在哪判断 |
|---|---|---|---|
| **`*:*:*`** | **权限码**（`permissions`） | **按钮级** | `plugins/auth.js` 的 `authPermission` |
| **`admin`** | **角色**（`roles`） | **路由级** | `plugins/auth.js` 的 `authRole` |

### 前端代码里的判断

```javascript
// src/plugins/auth.js
function authPermission(permission) {
  const all_permission = "*:*:*";                        // ★ 权限通配符
  const permissions = store.getters && store.getters.permissions
  if (permission && permission.length > 0) {
    return permissions.some(v => {
      return all_permission === v || v === permission    // 有通配符 or 精确匹配
    })
  }
  return false
}

function authRole(role) {
  const super_admin = "admin";                           // ★ 角色通配符
  const roles = store.getters && store.getters.roles
  if (role && role.length > 0) {
    return roles.some(v => {
      return super_admin === v || v === role
    })
  }
  return false
}
```

**两个是完全独立的机制。**

**实际上**：`isAdmin()` 的用户同时拿到 `roles=['admin']` 和 `permissions=['*:*:*']`，
所以两级都通。但如果你手动建一个角色，只给它 `permissions=['*:*:*']` 但不叫 `admin`，
**那它的按钮会全显示，但 `roles` 级的路由权限可能不通过**。

## 真相 3：⚠️ 前端三层都只是"界面美化"，**不是安全防线**

**这一条最重要，面试必问。**

### 前端权限能做什么

✅ **让用户看不到会报错的按钮**（体验优化）
✅ **减少无效请求**（没权限就别点了）
✅ **让界面看起来更专业**（不同角色看到不同界面）

### 前端权限**不能**做什么

❌ **阻止恶意用户调用接口**
❌ **保护数据安全**

### 证明：三行代码绕过所有前端权限

**假设一个"普通员工"角色，没有 `contract:contractDraft:remove` 权限。**
他在页面上**看不到"删除"按钮**（`v-hasPermi` 把它从 DOM 删了）。

**但他可以这么做**：

**方法 1：直接调接口**

```javascript
// F12 → Console 里敲
fetch('/dev-api/contract/contractDraft/123', {
  method: 'DELETE',
  headers: {
    'token': 'Bearer ' + document.cookie.match(/Admin-Token=([^;]+)/)[1]
  }
})
```

**⭐ 如果后端没做权限校验，这个请求就会成功删除数据。**

**方法 2：改 DOM（如果用了 `v-show` 而不是 `v-if`）**

```javascript
// 把按钮的 display 改回来
document.querySelector('.delete-btn').style.display = 'block'
```

**方法 3：直接改内存里的 permissions**

```javascript
// 如果能在控制台访问到 store（某些构建下可以）
window.__store.getters.permissions.push('contract:contractDraft:remove')
```

### ⭐ 正确的安全设计

**后端必须有 `@SaCheckPermission` 注解**：

**位置**：`zxcm-contract/src/main/java/com/ruoyi/contract/controller/ContractDraftController.java`

```java
@ApiOperation("删除合同草拟")
@SaCheckPermission("contract:contractDraft:remove")     // ★★★ 真正的防线
@Log(title = "合同草拟", businessType = BusinessType.DELETE)
@DeleteMapping("/{ids}")
public R<Void> remove(@PathVariable Long[] ids) {
    return toAjax(iContractDraftService.deleteWithValidByIds(Arrays.asList(ids), true));
}
```

**没有这个权限码的请求，后端会直接拒（抛 `NotPermissionException` → 返回 403）。**

### 一句话总结

```
前端权限 = 把按钮藏起来（防君子，不防小人）
后端权限 = 真正检查你有权没权（防线）
```

**类比**：

| | 前端权限 | 后端权限 |
|---|---|---|
| 像什么 | 电梯按钮贴个"禁止按"的纸条 | 电梯控制器不响应你的卡 |
| 能防住谁 | 老实人 | 所有人 |
| 撕掉纸条/直接撬开 | 照样能按 | **照样不能用** |

# 7.3 权限数据从哪来（后端视角）

## 完整链路

```
【登录】
  POST /login
    → 校验账号密码
    → 生成 token
    → 返回 { data: { token } }

【拿权限】
  GET /getInfo
    → SysPermissionService.getRolePermission(user)    → roles
    → SysPermissionService.getMenuPermission(user)    → permissions
    → 返回 { data: { user, roles, permissions } }
        ↓
  roles: ['admin']              或  ['common', 'contractAdmin']
  permissions: ['*:*:*']        或  ['contract:contractDraft:list', 'contract:contractDraft:add', ...]

【拿菜单】
  GET /getRouters
    → selectMenuTreeByUserId(userId)   → 已按角色过滤的菜单树
    → buildMenus()                     → RouterVo 列表
    → 返回
```

## ⭐ 数据库里的权限表关系

```
sys_user（用户）
  │ user_id
  ├──< sys_user_role（用户-角色关联）
  │      │ role_id
  │      └──< sys_role（角色）
  │             │ role_id, role_key（如 'admin' / 'common'）
  │             └──< sys_role_menu（角色-菜单关联）
  │                    │ menu_id
  │                    └──< sys_menu（菜单/按钮）
  │                           │ menu_id, menu_name, perms, menu_type
  │                           │ menu_type: M=目录 C=菜单 F=按钮
  │
  └──< sys_user_dept（用户-部门关联）→ 数据权限（只看本部门）
```

## ⭐ `sys_menu` 表怎么同时存"菜单"和"按钮"

| `menu_type` | 含义 | `component` | `perms` | 例子 |
|---|---|---|---|---|
| `M` | 目录 | `Layout` / `ParentView` | 空 | 合同管理 |
| `C` | 菜单 | 真实页面路径 | 如 `contract:contractDraft:list` | 合同草拟 |
| **`F`** | **按钮** | **空** | **如 `contract:contractDraft:add`** | 新增按钮 |

**⭐ 关键**：按钮权限（`F`）也是 `sys_menu` 表里的一行！
只是它没有 `component`，也不显示在菜单里，**只用于提供 `perms`**。

**所以"新增按钮的权限码"这个信息，是存在 `sys_menu` 表里的。**

**查按钮权限的 SQL**（大意）：

```sql
-- 查某个用户拥有的所有权限码（包括按钮的）
SELECT DISTINCT m.perms
FROM sys_menu m
LEFT JOIN sys_role_menu rm ON m.menu_id = rm.menu_id
LEFT JOIN sys_user_role ur ON rm.role_id = ur.role_id
WHERE ur.user_id = #{userId}
  AND m.perms IS NOT NULL
  AND m.perms != ''
```

**结果**：

```
contract:contractDraft:list
contract:contractDraft:add
contract:contractDraft:edit
contract:contractDraft:remove
contract:contractDraft:export
conf:billRule:list
...
```

**这就是前端 `store.getters.permissions` 里的内容。**

# 7.4 第 1 层：路由级权限

## 两种路由的权限处理方式

### 方式 A：`constantRoutes`（写死的，不需权限）

```javascript
// src/router/index.js
export const constantRoutes = [
  { path: '/login', component: () => import('@/views/login'), hidden: true },
  { path: '/404', component: () => import('@/views/error/404'), hidden: true },
  { path: '', component: Layout, redirect: '/index', children: [...] },
  // ...
]
```

**启动时直接注册，不需要任何权限判断。**

**为什么？** 因为页面本身要能被打开（登录页），或者内容不敏感（首页、404）。

### 方式 B：`dynamicRoutes`（写死的，**需要权限**）

```javascript
// src/router/index.js
export const dynamicRoutes = [
  {
    path: '/system/role-auth',
    component: Layout,
    hidden: true,
    permissions: ['system:role:edit'],          // ★ 权限码
    children: [
      {
        path: 'user/:roleId(\\d+)',
        component: () => import('@/views/system/role/authUser'),
        name: 'AuthUser',
        meta: { title: '分配用户', activeMenu: '/system/role' }
      }
    ]
  },
  {
    path: '/tool/gen-edit',
    component: Layout,
    hidden: true,
    permissions: ['tool:gen:edit'],             // ★ 权限码
    children: [...]
  },
  // ...
]
```

**注意 `permissions` 字段**（路由级的权限声明）。

## `filterDynamicRoutes()` —— 过滤逻辑

```javascript
// src/store/modules/permission.js:108
export function filterDynamicRoutes(routes) {
  const res = []
  routes.forEach(route => {
    if (route.permissions) {
      if (auth.hasPermiOr(route.permissions)) {     // ★ 有其中任意一个权限码
        res.push(route)
      }
    } else if (route.roles) {
      if (auth.hasRoleOr(route.roles)) {            // ★ 有其中任意一个角色
        res.push(route)
      }
    }
  })
  return res
}
```

**⭐ 逻辑**：

```
遍历 dynamicRoutes，对每一条：
  ├─ 有 permissions 字段？
  │    ├─ 用户有其中任意一个 → 保留
  │    └─ 没有 → 丢弃（不注册到路由表）
  ├─ 有 roles 字段？
  │    ├─ 用户有其中任意一个角色 → 保留
  │    └─ 没有 → 丢弃
  └─ 都没有？
       → 丢弃（⚠️ 注意！没有权限声明的 dynamicRoutes 会被丢弃）
```

**⚠️ 最后一条很重要**：如果一个 `dynamicRoutes` 里既没写 `permissions` 也没写 `roles`，
**它会被丢掉**（不会注册）。

**为什么这样设计？** 因为 `dynamicRoutes` 的定义就是"需要权限的页面"，
不写权限声明说明配置有误，宁可不注册。

## 调用位置

```javascript
// src/store/modules/permission.js:41
const asyncRoutes = filterDynamicRoutes(dynamicRoutes);
// ...
router.addRoutes(asyncRoutes);           // ★ 只注册有权限的
```

## ⭐ 两种"路由级权限"的对比

| | `constantRoutes` | `dynamicRoutes` | 后端菜单（`/getRouters`） |
|---|---|---|---|
| 谁定义 | 前端代码 | 前端代码 | **数据库** |
| 需要权限吗 | ❌ | ✅ | ✅（后端已筛） |
| 权限怎么判 | — | `filterDynamicRoutes` | 后端 SQL |
| 什么时候注册 | 启动 | 登录后 | 登录后 |
| 典型用途 | 登录、404、首页 | 隐藏在页面里的操作页 | 业务菜单 |

**⭐ 所以"路由级权限"有三个来源，都要理解。**

# 7.5 第 2 层：菜单级权限

## 这一层最简单

**因为后端已经筛好了。**

```javascript
// src/layout/components/Sidebar/index.vue
<sidebar-item
  v-for="(route, index) in sidebarRouters"
  :key="route.path + index"
  :item="route"
  :base-path="route.path"
/>
```

**`sidebarRouters` 里有什么，侧边栏就显示什么。**

## `sidebarRouters` 怎么来的

```javascript
// src/store/modules/permission.js
const sidebarRoutes = filterAsyncRouter(sdata)                          // 翻译 component
commit('SET_SIDEBAR_ROUTERS', constantRoutes.concat(sidebarRoutes))     // 存进 state
```

**所以是**：

```
后端 selectMenuTreeByUserId（已按角色过滤）
  → buildMenus（转 RouterVo）
    → 前端 filterAsyncRouter（翻译 component）
      → SET_SIDEBAR_ROUTERS
        → Sidebar 的 v-for
```

## ⚠️ 前端真的没做任何过滤吗

**严格说**：前端对 `sidebarRouters` **没做权限过滤**，
但做了**"隐藏"过滤**（`hidden: true` 的不显示）。

```javascript
// SidebarItem.vue 里
<template v-if="hasOneShowingChild(item.children,item) && ...">
```

`hasOneShowingChild` 会跳过 `hidden: true` 的项。

**但 `hidden` 不是权限**，只是"不显示在菜单里"（比如详情页、编辑页）。

## ⭐ `hidden` vs "没权限" 的区别

| 概念 | 含义 | 后端返回吗 |
|---|---|---|
| `hidden: true` | **有权限，但不想显示在菜单里** | ✅ 返回（前端不渲染菜单项） |
| **没权限** | **后端根本不返回** | ❌ 不返回 |

**例子**：

```javascript
// 详情页：有权限，但不显示在菜单里（从列表点进去）
{
  path: '/system/dict-data',
  component: Layout,
  hidden: true,                          // ★ 不显示在菜单
  permissions: ['system:dict:list'],
  children: [...]
}
```

**所以 `hidden` 是"界面上藏起来"，不是权限控制。**

# 7.6 第 3 层：按钮级权限（`v-hasPermi`）

## 页面里怎么用

```html
<!-- 有权限才显示这个按钮 -->
<el-button
  v-hasPermi="['contract:contractDraft:add']"
  type="primary"
  @click="handleAdd"
>新增</el-button>

<!-- 也可以要求多个（有其中任意一个就显示） -->
<el-button v-hasPermi="['a:b:c', 'd:e:f']">操作</el-button>

<!-- 角色级（较少用） -->
<el-button v-hasRole="['admin']">仅管理员可见</el-button>

<!-- 反向：没有这个权限才显示 -->
<el-button v-not-hasPermi="['a:b:c']">非管理员可见</el-button>
```

## 实现（`directive/permission/hasPermi.js`）

**完整代码（28 行）**：

```javascript
/**
 * v-hasPermi 操作权限处理
 * Copyright (c) 2019 ruoyi
 */

import store from '@/store'

export default {
  inserted(el, binding, vnode) {
    const { value } = binding
    const all_permission = "*:*:*";
    const permissions = store.getters && store.getters.permissions

    if (value && value instanceof Array && value.length > 0) {
      const permissionFlag = value

      const hasPermissions = permissions.some(permission => {
        return all_permission === permission || permissionFlag.includes(permission)
      })

      if (!hasPermissions) {
        el.parentNode && el.parentNode.removeChild(el)      // ★★★ 从 DOM 删掉
      }
    } else {
      throw new Error(`请设置操作权限标签值`)
    }
  }
}
```

## 逐段讲解

### ① `inserted` 是 Vue 指令的钩子

```javascript
export default {
  inserted(el, binding, vnode) { ... }
}
```

**Vue 自定义指令的钩子**：

| 钩子 | 时机 |
|---|---|
| `bind` | 指令第一次绑定到元素时（DOM 还没插入） |
| **`inserted`** | **元素插入到 DOM 时**（能拿到真实 DOM） |
| `update` | 组件更新时 |
| `componentUpdated` | 组件和子组件都更新完 |
| `unbind` | 指令解绑时 |

**为什么用 `inserted`？** 因为需要 `el.parentNode`（元素插入后才有父节点）。

**类比后端**：≈ 一个 AOP 切面，切在"元素插入 DOM"这个切点。

### ② 三个参数

| 参数 | 是什么 |
|---|---|
| `el` | 指令绑定的 DOM 元素（`<button>`） |
| `binding` | 指令信息对象，`binding.value` 就是 `v-hasPermi="..."` 里的值 |
| `vnode` | 虚拟节点（这里没用到） |

```javascript
const { value } = binding        // 解构出 value
```

**如果页面写的是 `v-hasPermi="['a:b:c']"`，那 `value` 就是 `['a:b:c']`。**

### ③ 参数校验

```javascript
if (value && value instanceof Array && value.length > 0) {
  // 正常处理
} else {
  throw new Error(`请设置操作权限标签值`)
}
```

**三个条件都要满足**：

1. `value` 非空
2. `value` 是**数组**
3. 数组长度 > 0

**⚠️ 为什么必须传数组？**

```html
v-hasPermi="['a:b:c']"      <!-- ✅ 数组 -->
v-hasPermi="a:b:c"          // ❌ 字符串 → 走到 throw 报错
```

**这是新手最常见的误用。**

**为什么要 `throw` 而不是静默？**

因为"指令没传值"是**开发者的编码错误**。
如果静默失败，开发者会以为"权限控制生效了"（其实是写错了）。

### ④ 核心判断（最关键）

```javascript
const hasPermissions = permissions.some(permission => {
  return all_permission === permission || permissionFlag.includes(permission)
})
```

**读法**：遍历**用户拥有的所有权限码**（`permissions`），

- `all_permission === permission` → 用户有 `*:*:*`（超级管理员）
- `permissionFlag.includes(permission)` → **页面要求的数组里**包含用户的这个权限码

**⭐ 方向很重要**：

```javascript
permissionFlag.includes(permission)
//  ↑ 页面要求的数组        ↑ 用户拥有的某个权限码
```

**这是"页面要求里有用户这个吗"，不是"用户里有页面这个吗"。**

**为什么方向是反的也能对？**

因为 `some` 遍历的是**用户的权限码**。
对每个用户权限码，检查它是否在页面要求的列表里。

**效果等价于**：

```javascript
permissionFlag.some(p => permissions.includes(p))
```

**两种写法结果一样，只是遍历的对象不同。**

### ⑤ ⭐ 删掉元素（核心一行）

```javascript
if (!hasPermissions) {
  el.parentNode && el.parentNode.removeChild(el)
}
```

**`el.parentNode &&` 的作用**：短路求值，如果 `parentNode` 是 `null`
（元素没有父节点），后面的 `removeChild` 就不执行（避免报错）。

**效果**：按钮**彻底从 DOM 消失**，不是 `display: none`。

**用户 F12 也看不到这个元素。**

**⚠️ 但如前所述，这不是安全防线**（用户可以直接调接口）。

## 为什么用 `removeChild` 而不是 `v-if`

**对比**：

```html
<!-- 方案 A：v-if -->
<el-button v-if="hasPermission('contract:add')">新增</el-button>
<!-- 需要在每个页面写 computed：hasPermission() 方法 -->

<!-- 方案 B：v-hasPermi 指令 -->
<el-button v-hasPermi="['contract:add']">新增</el-button>
<!-- 指令内部自己处理逻辑 -->
```

**`v-hasPermi` 的优势**：

| | `v-if` 方案 | `v-hasPermi` 方案 |
|---|---|---|
| 每个页面要写 | `hasPermission()` 方法 | 什么都不用写 |
| 模板可读性 | 一般 | **简洁** |
| 复用 | 差 | **好**（全局指令） |

**所以项目选了指令方案。**

## 指令的注册

**位置**：`src/directive/index.js`

```javascript
import hasPermi from './permission/hasPermi'
import hasRole from './permission/hasRole'
import notHasPermi from './permission/notHasPermi'

const install = function(Vue) {
  Vue.directive('hasPermi', hasPermi)
  Vue.directive('hasRole', hasRole)
  Vue.directive('not-hasPermi', notHasPermi)
}

export default { install }
```

**然后在 `main.js` 里**：

```javascript
import directive from "./directive"
Vue.use(directive)                 // 触发 install(Vue)
```

**⭐ 这就是 `v-hasPermi` 能用的原因。**

# 7.7 `plugins/auth.js` 的 6 个函数

**位置**：`src/plugins/auth.js`（57 行）

```javascript
import store from '@/store'

// ---- 私有函数：判断单个权限码 ----
function authPermission(permission) {
  const all_permission = "*:*:*";
  const permissions = store.getters && store.getters.permissions
  if (permission && permission.length > 0) {
    return permissions.some(v => {
      return all_permission === v || v === permission
    })
  } else {
    return false
  }
}

// ---- 私有函数：判断单个角色 ----
function authRole(role) {
  const super_admin = "admin";
  const roles = store.getters && store.getters.roles
  if (role && role.length > 0) {
    return roles.some(v => {
      return super_admin === v || v === role
    })
  } else {
    return false
  }
}

// ---- 对外暴露 6 个方法 ----
export default {
  // ① 验证用户是否具备某权限
  hasPermi(permission) {
    return authPermission(permission);
  },

  // ② 验证用户是否含有指定权限，只需包含其中一个
  hasPermiOr(permissions) {
    return permissions.some(item => {
      return authPermission(item)
    })
  },

  // ③ 验证用户是否含有指定权限，必须全部拥有
  hasPermiAnd(permissions) {
    return permissions.every(item => {
      return authPermission(item)
    })
  },

  // ④ 验证用户是否具备某角色
  hasRole(role) {
    return authRole(role);
  },

  // ⑤ 验证用户是否含有指定角色，只需包含其中一个
  hasRoleOr(roles) {
    return roles.some(item => {
      return authRole(item)
    })
  },

  // ⑥ 验证用户是否含有指定角色，必须全部拥有
  hasRoleAnd(roles) {
    return roles.every(item => {
      return authRole(item)
    })
  }
}
```

## ⭐ `.some()` vs `.every()`（关键区别）

| 方法 | 含义 | 提前终止 |
|---|---|---|
| `.some(f)` | **有一个**满足就 `true` | 找到第一个**满足的**就停 |
| `.every(f)` | **全部**满足才 `true` | 找到第一个**不满足的**就停 |

**例子**：

```javascript
const permissions = ['a', 'b']

hasPermiOr(['a', 'x'])      // true   （有 a）
hasPermiOr(['x', 'y'])      // false  （都没有）
hasPermiAnd(['a', 'b'])     // true   （都有）
hasPermiAnd(['a', 'x'])     // false  （缺 x）
```

## 谁在用这 6 个函数

| 调用方 | 用的哪个 | 用途 |
|---|---|---|
| `directive/permission/hasPermi.js` | 自己实现（逻辑类似） | 按钮隐藏 |
| `store/modules/permission.js:112` | `hasPermiOr` / `hasRoleOr` | **路由级过滤** |
| 页面里 `this.$auth.hasPermi('x')` | 任意 | 手写判断（少见） |

## `this.$auth` 怎么来的

**位置**：`src/plugins/index.js`

```javascript
import auth from './auth'
import modal from './modal'
import tab from './tab'
import download from './download'

export default {
  install(Vue) {
    Vue.prototype.$auth = auth
    Vue.prototype.$modal = modal
    Vue.prototype.$tab = tab
    Vue.prototype.$download = download
  }

```

**`main.js` 里 `Vue.use(plugins)` 就注册了。**

**所以页面里能写**：

```javascript

  // 手动判断
}
```

**⭐ 但更推荐用 `v-hasPermi` 指令**（更简洁）。

# 7.9 完整权限检查流程

**把三层串起来。**

```
【① 登录时】
POST /login → 得到 token
  ↓
【② 拿权限】
GET /getInfo
  → 后端 SysPermissionService 查数据库
  → 返回 roles: ['admin'] / permissions: ['*:*:*']
  ↓
前端 store/modules/user.js 的 GetInfo
  → commit('SET_ROLES', roles)
  → commit('SET_PERMISSIONS', permissions)
  ↓
store.getters.roles / store.getters.permissions
  ↓
【③ 路由级：建路由表】
GET /getRouters
  → 后端按角色过滤，只返回有权限的菜单
  ↓
前端 filterAsyncRouter 翻译 component
  ↓
filterDynamicRoutes(dynamicRoutes)    ← 用 hasPermiOr 判断写死的权限路由
  ↓
router.addRoutes(有权限的路由)
  ↓
【④ 菜单级：渲染侧边栏】
sidebarRouters（就是后端返回的）→ v-for → 菜单
  ↓
【⑤ 按钮级：渲染页面】
页面渲染时，v-hasPermi 指令的 inserted 钩子触发
  ↓
读 store.getters.permissions
  ↓
比对页面写的权限码
  ↓
有 → 保留按钮
没有 → el.parentNode.removeChild(el)  → 按钮消失
  ↓
【⑥ 用户点按钮 → 发请求】
  ↓
【⑦ 后端 @SaCheckPermission 检查】  ★★★ 真正的防线
  ↓
有权限 → 执行
没权限 → 抛 NotPermissionException → 403
```

## ⭐ 关键节点标红

| 关键点 | 说明 |
|---|---|
| **后端 `selectMenuTreeByUserId`** | 决定返回哪些菜单（前端拿不到没权限的） |
| **`filterDynamicRoutes`** | 决定注册哪些写死的权限路由 |
| **`v-hasPermi` 的 `removeChild`** | 决定按钮显不显示 |
| **后端 `@SaCheckPermission`** | ⭐ **唯一真正的防线** |

# 7.10 ⚠️ 为什么前端权限不安全（含绕过演示）

## 三个绕过方法（演示用，不要真干）

### 方法 1：直接调接口（最简单）

**前提**：知道接口地址和参数。

```javascript
// F12 → Console
const token = document.cookie.match(/Admin-Token=([^;]+)/)[1]

fetch('/dev-api/contract/contractDraft/123', {
  method: 'DELETE',
  headers: { 'token': 'Bearer ' + token }
}).then(r => r.json()).then(console.log)
```

**⭐ 如果后端有 `@SaCheckPermission`，会返回 403（安全）。**
**如果没有，删除成功（危险）。**

### 方法 2：改 DOM（针对 `v-show`）

**如果权限控制用的是 `v-show`（不是 `v-hasPermi`）**：

```javascript
// F12 → Elements → 找到按钮 → 把 style="display: none" 删掉
document.querySelector('.delete-btn').style.display = 'inline-block'
```

**⚠️ 项目用的是 `v-hasPermi`（`removeChild`），所以这个方法无效**
（元素已经从 DOM 删了，找不到）。

**但可以用方法 3。**

### 方法 3：改内存里的权限（某些情况下可行）

```javascript
// 如果构建时暴露了 Vue 实例或 store
// 某些脚手架会挂 window.$vm / window.$store
window.$store.getters.permissions.push('contract:contractDraft:remove')

// 然后按钮会重新渲染时出现（但如果已经 removeChild 了，需要重新渲染页面）
```

**⚠️ 项目的构建通常不会暴露这些到 `window`，所以不容易成功。**

**但理论上**：如果能拿到 Vue 实例，就能改 `store.state.user.permissions`。

## ⭐ 结论

| 前端权限 | 能防住 | 防不住 |
|---|---|---|
| `v-hasPermi` | 普通用户误点 | 会用 F12 的人 |
| 路由级权限 | 直接输 URL 访问 | 直接调接口 |
| 菜单隐藏 | 找菜单的人 | 知道 URL 的人 |

**所以：前端权限 = 用户体验优化，不是安全。**

## 真正安全的做法

### 后端三层防护

**① 接口级：`@SaCheckPermission`**

```java
@SaCheckPermission("contract:contractDraft:remove")
@DeleteMapping("/{ids}")
public R<Void> remove(@PathVariable Long[] ids) { ... }
```

**② 数据级：`@DataPermission`（只看本部门数据）**

```java
@DataPermission({
    @DataColumn(key = "deptName", value = "d.dept_id")
})
public TableDataInfo<ContractDraftVo> queryPageList(...) { ... }
```

**③ 租户级：自动加 `tenant_id` 条件**

（RuoYi 的多租户插件自动处理）

### 一句话总结

```
前端做权限 = 让界面好看
后端做权限 = 让数据安全
两者都要做，但只有后端是"防线"
```

# 7.11 如何正确设计权限

## 加一个新按钮的完整清单

**场景**：给"合同草拟"页面加一个"批量删除"按钮。

### ① 数据库：加一条 `F` 类型的菜单记录

```sql
INSERT INTO sys_menu (
  menu_name, parent_id, order_num, path, component, menu_type,
  visible, status, perms, icon, create_by, create_time
) VALUES (
  '批量删除',                          -- 按钮名
  (SELECT menu_id FROM (SELECT menu_id FROM sys_menu WHERE menu_name='合同草拟') t),
  5,                                   -- 排序
  '',                                  -- ★ 按钮没有 path
  '',                                  -- ★ 按钮没有 component
  'F',                                 -- ★ F = 按钮
  '0', '0',
  'contract:contractDraft:batchRemove', -- ★ 权限码
  '#',
  'admin', sysdate()
);
```

**⭐ 按钮的 `path` 和 `component` 都是空串。**

### ② 给角色分配这个按钮

```sql
INSERT INTO sys_role_menu (role_id, menu_id)
VALUES (1, <刚插入的menu_id>);          -- role_id=1 是 admin
```

### ③ 后端：加注解

**位置**：`zxcm-contract/src/main/java/com/ruoyi/contract/controller/ContractDraftController.java`

```java
@ApiOperation("批量删除合同草拟")
@SaCheckPermission("contract:contractDraft:batchRemove")    // ★ 必须和数据库一致
@Log(title = "合同草拟", businessType = BusinessType.DELETE)
@DeleteMapping("/batch/{ids}")
public R<Void> batchRemove(@PathVariable Long[] ids) {
    return toAjax(iContractDraftService.deleteWithValidByIds(Arrays.asList(ids), true));
}
```

### ④ 前端：加按钮 + 指令

**位置**：`src/views/contract/contractDraft/index.vue`

```html
<el-col :span="1.5">
  <el-button
    v-hasPermi="['contract:contractDraft:batchRemove']"      <!-- ★ 和数据库一致 -->
    type="danger"
    icon="el-icon-delete"
    size="mini"
    :disabled="multiple"                                      <!-- 没选中时禁用 -->
    @click="handleBatchRemove"
  >批量删除</el-button>
</el-col>
```

### ⑤ 前端：加方法

```javascript
methods: {
  handleBatchRemove() {
    this.$modal.confirm('确认删除选中的 ' + this.ids.length + ' 条记录？')
      .then(() => {
        this.loading = true
        return batchRemoveContractDraft(this.ids)
      })
      .then(() => {
        this.getList()
        this.$modal.msgSuccess('删除成功')
      })
      .finally(() => {
        this.loading = false
      })
  }
}
```

### ⑥ 前端：加 api 函数

**位置**：`src/api/contract/contractDraft.js`

```javascript
// 批量删除
export function batchRemoveContractDraft(ids) {
  return request({
    url: '/contract/contractDraft/batch/' + ids.join(','),
    method: 'delete'
  })
}
```

### ⑦ 刷新页面测试

**Ctrl+F5 强刷** → 应该看到"批量删除"按钮。

**测试方法**：

1. 用 admin 登录 → **能看到按钮** ✅
2. 新建一个角色（不给 `batchRemove` 权限）→ 用那个用户登录 → **看不到按钮** ✅
3. **用普通用户直接调接口** → 后端返回 **403** ✅（这才是安全）

## 常见错误对照表

| 错误 | 现象 | 排查 |
|---|---|---|
| 数据库 `perms` 拼错 | 按钮不显示 | 对比前后端字符串 |
| 数据库没插按钮记录 | 按钮不显示 | 查 `sys_menu` |
| 角色没分配 | 按钮不显示 | 查 `sys_role_menu` |
| 前端 `v-hasPermi` 写成字符串 | **控制台报错** `请设置操作权限标签值` | 改成数组 |
| 后端漏了 `@SaCheckPermission` | ⚠️ **按钮藏了但接口能调（危险）** | 加注解 |
| 后端注解拼错 | 所有人都 403 | 对比数据库 |

**只有后端 `@SaCheckPermission` 会拦住。**

## 练习 3：故意绕过

**任务**：写一个没有权限的用户，然后尝试绕过。

1. 系统管理 → 角色管理 → 新建角色"测试角色"，**不给任何合同权限**
2. 系统管理 → 用户管理 → 新建用户，分配"测试角色"
3. 用那个用户登录
4. 观察：**看不到合同相关菜单**（后端不返回）
5. F12 → Console → 手动调 `/getInfo` 看 `permissions`（应该没有合同权限）
6. **手动调合同列表接口**：

```javascript
const token = document.cookie.match(/Admin-Token=([^;]+)/)[1]

fetch('/dev-api/contract/contractDraft/list?pageNum=1&pageSize=10', {
  headers: { 'token': 'Bearer ' + token }
}).then(r => r.json()).then(console.log)
```

**预期结果**：

- **如果后端有 `@SaCheckPermission`** → 返回 403 ✅
- **如果后端没有** → 返回数据 ❌（这是漏洞）

**⭐ 这个实验能让你彻底明白**：前端藏菜单藏按钮，和"数据安全"是两件事。

## 练习 4：读懂 `some` 和 `every`

```javascript
const permissions = ['a:b:c', 'd:e:f']

// 下面四个表达式分别是什么？
1) permissions.some(p => p === 'a:b:c')
2) permissions.some(p => p === 'x:y:z')
3) permissions.every(p => p === 'a:b:c')
4) permissions.every(p => p.startsWith('a'))
```

<details>
<summary>答案</summary>

1. `true`（有 `a:b:c`）
2. `false`（没有 `x:y:z`）
3. `false`（不是所有都是 `a:b:c`）
4. `false`（`d:e:f` 不以 `a` 开头）

**所以 `hasPermiOr` 用 `some`，`hasPermiAnd` 用 `every`。**
</details>

# 本章自测

1. 权限有哪三层？各控制什么？
2. 为什么说"前端几乎不判断权限"？
3. `*:*:*` 和 `admin` 分别属于什么？各控制哪一层？
4. 这两个通配符是数据库配的还是后端硬编码的？
5. `sys_menu` 表的 `menu_type` 有哪三种？`F` 是什么？
6. `constantRoutes` 和 `dynamicRoutes` 在权限上有什么区别？
7. 为什么 `dynamicRoutes` 里不写 `permissions` 会被丢弃？
8. `hidden: true` 是权限控制吗？
9. `v-hasPermi` 用什么方式隐藏按钮？和 `v-show` 有什么区别？
10. `v-hasPermi="'a:b:c'"`（字符串）会怎样？
11. `v-hasPermi` 里 `permissionFlag.includes(permission)` 的方向是什么？
12. 前端权限能防止恶意用户删数据吗？为什么？
13. 真正的防线在哪？
14. 加一个按钮要改几个地方？

<details>
<summary>答案</summary>

1. **路由级**（能不能打开页面）、**菜单级**（侧边栏显示什么）、**按钮级**（页面显示什么按钮）
2. 因为**菜单和权限码都是后端给的**（`/getRouters` 已按角色过滤，`/getInfo` 直接给权限码列表）。前端只负责显示
3. `*:*:*` 是**权限码通配符**（按钮级）；`admin` 是**角色通配符**（路由级）
4. **后端 Java 硬编码**（`SysPermissionService` 里 `perms.add("*:*:*")` / `roles.add("admin")`）
5. `M`=目录、`C`=菜单、**`F`=按钮**（只提供 `perms`，没有 path 和 component）
6. `constantRoutes` **启动就注册，不需权限**；`dynamicRoutes` **登录后按权限过滤**再注册
7. 因为 `dynamicRoutes` 的定义就是"需要权限的页面"，不写权限声明说明配置有误，宁可不注册
8. **不是**。`hidden` 只是"不显示在菜单里"（如详情页），但有权限、路由仍然注册
9. **`el.parentNode.removeChild(el)`** 彻底从 DOM 删除；`v-show` 只是 `display: none`（F12 能看到元素、能改回来）
10. **报错** `请设置操作权限标签值`（因为 `instanceof Array` 判断失败）
11. 遍历**用户的权限码**，检查它是否在**页面要求的数组**里（`permissionFlag` 是页面写的）
12. **不能**。用户可以直接用 `fetch` 调接口，绕过所有前端判断
13. **后端的 `@SaCheckPermission` 注解**
14. **数据库**（`sys_menu` 插 `F` 类型记录 + `sys_role_menu` 分配）、**后端**（`@SaCheckPermission`）、**前端**（`v-hasPermi` 指令 + 方法 + api 函数）
</details>
